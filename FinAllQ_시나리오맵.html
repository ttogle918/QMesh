🔴 무엇이 있고 무엇이 없는가 — S5를 예로

🔴 S5가 "구현 중"인 이유는 결재 로직이 없어서가 아닙니다. 요청을 받을 문이 없을 뿐이고, 문 뒤의 레일 — 2단 승인·FDS·감사·잔액 차감 — 은 개인/기업 양쪽 모드로 이미 실증됐습니다. A2A 관점에서 남은 일은 기존 REST 흐름을 Agent Card 스킬로 감싸는 어댑터입니다.

FinAllQ 내부 구조 — 왜 이렇게 나눴나

코어와 모델을 프로세스 단위로 갈랐습니다. 같은 프로세스에 모델을 태우면 배포는 쉽지만 모델이 죽을 때 이체도 같이 죽습니다. 사이에 차단기를 둬 AI 장애가 코어로 번지지 않게 했습니다 — A2A에서 남의 에이전트를 부를 때도 같은 경계가 필요합니다.

쓴 기법 — 왜 그렇게했는지까지
오케스트레이션LangGraph 상태 그래프

계획 → 툴 실행 → 답 조립을 노드로 나눠 어느 단계에서 무엇을 했는지 추적됩니다. 🔴 계획은 규칙 기반 키워드 매칭이고 조립은 템플릿입니다 — LLM을 안 쓴 이유는 왜 그 답이 나왔는지 설명할 수 없게 되기 때문입니다.

보안화이트리스트 기반 차단

감사 로그와 AI 전송 페이로드는 등재된 키만 나갑니다. 블랙리스트였다면 새 필드가 생길 때마다 빠뜨릴 위험이 생깁니다 — 계좌번호·금액은 목록에 없어서 구조적으로 실릴 수 없습니다.

안전이중 방어 (규칙 → 모델)

한도 규칙을 먼저 통과해야 FDS에 도달합니다. 순서 자체가 통제라서, 모델이 놓쳐도 규칙에서 막힙니다. 반대로 두면 "모델이 놓쳐도 막힌다"는 성질이 사라집니다.

인가직무 분리 매트릭스

판정 축을 전부 곱한 18칸 표를 먼저 그리고 칸 수만큼 테스트를 씁니다. 허용은 4칸뿐이고, 관리자는 결재자가 아닙니다 — 시스템 권한과 금전 승인 권한을 한 사람에게 합치지 않습니다.

불변식열거가 아니라 "벗어나는가"

가드를 새 값 == X로 쓰면 값이 추가될 때마다 조용히 뚫립니다. "권한에서 벗어나는 전이인가"로 표현해 새 역할이 생겨도 가드가 유지됩니다 — 실제로 한 번 뚫린 뒤 얻은 교훈입니다.

감사append-only · 수정 경로 없음

성공뿐 아니라 차단·거부된 시도도 남습니다. 다만 이건 애플리케이션 계약이지 DB 제약이 아니라는 한계를 문서에 남겨뒀습니다.

인증Access=메모리 · Refresh=HttpOnly

토큰을 localStorage에 두지 않습니다. 초대 토큰도 같은 원칙이라 화면에 한 번만 보여주고 저장하지 않습니다(스토리지 미저장을 테스트로 고정).

초대서버가 역할을 고정

초대 요청 본문에서 역할·권한을 받지 않습니다. 발급 경로가 서버에서 값을 정해서, 담당자 경로로는 절대 관리자를 만들 수 없습니다 — 권한 상승 경로를 구조로 차단합니다.

시간서비스 타임존 명시

"하루"의 경계를 JVM 기본값에 맡기면 컨테이너 설정이 판정을 좌우합니다. 명시 설정 + Clock 주입으로 고정하고, 잘못된 값이면 조용히 넘어가지 않고 부팅에 실패시킵니다.

테스트testcontainers 격리 · shuffle 상시

테스트가 공유 DB에 붙어 실행마다 잔재가 쌓이던 것을 격리했습니다. 프론트는 실행 순서를 매번 섞어 돌립니다 — 순서에 기대는 테스트는 언젠가 무작위로 깨지는데, 그때는 원인을 아무도 모릅니다.

스키마Flyway 롤포워드

적용된 마이그레이션은 절대 수정하지 않고 새 버전을 얹습니다. 체크섬이 깨지면 배포된 환경과 로컬이 갈라집니다.

장애Fail-soft + 차단기

AI 노드가 죽어도 코어는 돕니다. 🔴 다만 빠진 기능을 조용히 숨기지 않고 배너로 알립니다 — 실패가 실패로 보이지 않는 것이 더 나쁩니다.

판정 일관성쓰기·읽기가 판정 로직을 공유

여신 자동거절(신청 시점)과 심사 근거 재조회(화면 표시)가 같은 순수 static 헬퍼를 부릅니다(Sprint 15). 각자 구현하면 "신청 땐 거절인데 화면엔 통과"처럼 DB와 화면이 다른 말을 하게 됩니다 — 판정은 한 곳에만 존재해야 합니다.

비용재조회 전 캐시부터 본다

목록 화면에서 상세를 N건 미리 긁지 않고, 펼친 행 1건만 조회 후 loanId로 캐시합니다(절대 원칙 8). 신규 라이브러리 0개 — 기존 컴포넌트(펼침 행·모달)를 재사용하는 것이 이 프로젝트 전반의 기본값입니다.

A2A로 가려면 남은 일 — ① Agent Card(/.well-known/agent-card.json)로 request-withdrawal·assess-loan 같은 스킬을 선언 ② :9001 얼굴 포트를 열고 기존 REST 흐름에 연결하는 어댑터 ③ Task 생명주기 중 input-required(사람 승인 대기) 상태를 기존 결재함에 매핑 ④ request_chain_id를 감사 로그에 추가해 멀티홉 추적.
🟢 ③은 이미 있는 결재함을 그대로 쓰면 됩니다 — 승인 대기라는 개념이 이미 도메인에 있습니다.

③ 세 프로젝트가 주고받는 요청 (통신 다이어그램)

경계 넘는 시나리오 10개 · S5·S6·S7·S8·S11~S16

S1~S4·S9·S10·S17·S18·S19~S29는 각 프로젝트 안에서만 끝나는 흐름이고, 여기 나오는 건 한 프로젝트가 다른 프로젝트에 작업을 맡기는 연계 요청입니다.

④ 용어 사전

본문에 나온 어려운 말 모음
A2A

Agent to Agent. 서로 다른 프로젝트(=다른 회사)의 AI끼리 직접 요청을 주고받는 것.

멀티홉

A가 B에게 요청하고, B가 다시 C에게 물어보는 것처럼 두 단계 이상 거쳐 전달되는 요청.

2단 승인

돈이 실제로 나가기 전에 사람이 두 번 확인하는 것. 예: 공장 팀장이 한 번, 은행 재무담당이 한 번.

human-in-the-loop

AI가 결정을 대신하지 않고, 마지막 확정은 항상 사람이 누르게 만드는 설계 원칙.

FDS

이상거래 탐지 시스템. 수상한 돈 요청을 자동으로 걸러내는 장치.

RAG

문서(약관·매뉴얼)에서 관련 부분을 찾아서 그걸 근거로 답하는 방식. 지어내지 않고 찾아서 답함.

request_chain_id

요청이 여러 프로젝트를 거칠 때, "이게 원래 어디서 시작된 요청인지" 추적하는 번호표.

승인 큐

확인·승인을 기다리는 요청들이 쌓이는 대기 목록 화면.

Agent Card

AI 에이전트의 명함. "나는 이런 일을 할 수 있다"를 정해진 주소(/.well-known/agent-card.json)에 적어두면 다른 회사 AI가 읽고 일을 맡길 수 있음. FinAllQ엔 아직 없음.

앵커(anchor)

회사에 처음 만들어지는 결재 담당자. 은행이 지정해줘야 생기고, 이 사람이 생겨야 회사가 직원을 초대할 수 있음. 없으면 회사는 사람 0명인 빈 껍데기.

결재 라인

기업 고객에서 "누가 돈 나가는 걸 승인하나"를 정한 규칙. 요청자와 결재자가 반드시 달라야 하고, 시스템 관리자는 결재자가 아님.

차단기

바깥 서비스(AI 모델 등)가 계속 실패하면 잠시 호출을 끊어버리는 장치. 한 곳이 죽었을 때 전체가 같이 느려지거나 죽는 걸 막음.

화이트리스트 차단

"내보내면 안 되는 것"을 적는 대신 "내보내도 되는 것만" 적는 방식. 새 항목이 생겨도 목록에 없으면 자동으로 막히므로 빠뜨릴 위험이 없음.

LangGraph

AI가 여러 단계를 거쳐 일하는 과정을 그래프(노드와 연결)로 표현하는 도구. 어느 단계에서 뭘 했는지 추적할 수 있음.

Fail-soft

일부가 고장나도 전체가 멈추지 않고 되는 것만이라도 돌려주는 설계. 단 빠진 게 있다는 걸 사용자에게 알려야 함.

🆕 재무부 승인 게이트 신설 — S1·S5 발신 시점 변경 (2026-08-24, D119). 팀장 승인(1차) 다음에 MaintQ 자체 재무부 승인(2차) 단계가 새로 생겼습니다 — 예산 한도·1일 누적 한도·FDS(이상거래탐지)·SoD(직무분리) 4종 내부통제 판정을 재무부 소속 계정(department=="finance")만 통과시킬 수 있습니다. 이 변경이 A2A와 직결됩니다: FinAllQ로 나가는 출금 요청(request-withdrawal, S5)이 이제 팀장 승인이 아니라 재무부 승인 시점에 발신됩니다(POST /api/po/{id}/approve는 더 이상 A2A를 발신하지 않고, 새 POST /api/po/{id}/finance-approve가 그 자리를 대신함). payload 스키마 자체는 무변경 — approved_by는 여전히 팀장 ID입니다. 재무부 승인 시 사람 승인용 3번째 문서(자금집행요청서, doc3)도 함께 자동 렌더됩니다(D118이 미뤄뒀던 항목). 상세 시퀀스는 a2a-contract-and-data-flow.html §4.1 참고.

FinAllQ가 "레일은 깔렸고 문이 없다", InsuQ가 "답하는 능력은 됐고 조회할 대장이 없다"였다면 — MaintQ는 "MVP(M1~M4) 및 확장 Sprint 5~18 전수를 완주하여 도구 20종과 21개 라우트가 가동 중"입니다. 2026-08-12 related_parts 사람 최종 승인으로 D12 게이트가 해제되어 5지표 모두 판정 가능해졌으며, 세 프로젝트 중 유일하게 지표를 회차 반복으로 측정합니다. 2026-08-20 부서·권한 분리(D108)로 재무부 계정 축이 생겼고, Sprint 15(P11)가 끝나 3번째 기종 IE5가 lookup_error_code 조회 경로에 편입됐습니다(안전 문구·RAG·물리 자산은 의도적으로 범위 밖). ✅ A2A 실통신 2종 구현 완료 (2026-08-21). MaintQ 아웃바운드 클라이언트(call_skill·record_a2a_trace)와 suppliers 계좌번호 마이그레이션이 완료되었습니다. S5 발주 출금 요청(MaintQ→FinAllQ :9101) 및 약관 근거 실시간 질의(MaintQ→InsuQ :9102)가 E2E 실통신으로 검증되었으며, traces 테이블에 request_chain_id와 원본 응답이 불변 기록됩니다.
🔧 Sprint 16(2026-08-23~24) — 시나리오 진행도 변화 없음, 내부 신뢰성 인프라 갱신. MaintQ가 DB를 SQLite에서 Postgres로 전환했고(D116, Supabase 등 관리형 Postgres 배포 대응), 매뉴얼 검색을 키워드 단독에서 키워드+임베딩(dense) 하이브리드로 확장했습니다(D117, NVIDIA API nvidia/nemotron-3-embed-1b). 이 갱신 과정에서 미포팅 A2A 계약 스파이크 2종이 Postgres 위에서 실제로 깨져 있던 것을 발견·수정했고(격리 미비로 공유 DB에 실제 쓰기 사고가 있었음), 같은 결함으로 미반영 pytest 8파일(46/86 실패)도 함께 고쳤습니다 — 위 A2A 실통신 2종의 구현 판정 자체는 바뀌지 않습니다(회귀만 더 견고해짐). 통신 프로토콜·시나리오 번호·진행률 보드는 이 갱신과 무관합니다.
✅ A2A 3번째 실통신 — S13/S8 담보대출 심사(assess-loan) E2E 성공 (2026-08-24). 앞서 막혀 있던 두 지점이 이번에 다 풀렸다: ① MaintQ→FinAllQ payload 필드가 A2A_Q 공식 계약과 어긋나 있던 걸 FinAllQ 쪽이 공식 계약대로 재작성(MaintQ 쪽은 원래 계약을 지키고 있어 무변경) ② FinAllQ→InsuQ 2차 홉(verify-collateral-insurance)이 미구현이었던 것도 해소. 실 응답: {"status":"completed","decision":"approved","collateral_check":{"coverage_amount":300000000.0,"sufficient":true}}. 같은 날 S5 출금 요청(request-withdrawal)에서도 실제 버그 하나를 찾아 고쳤다 — po_drafts.error_code가 NULL인 발주(에러코드 진단이 아닌 발주)를 승인하면 payload에 error_code: null이 그대로 실려 FinAllQ가 400으로 거부하던 것을 "" 로 고쳤다(수정 전에도 error_code가 있는 정상 케이스는 이미 동작했었다). lookup-clause는 코드·계약 모두 그대로지만 지금은 MaintQ 쪽 서비스 자격증명 미설정으로 런타임에 막혀 있다(코드 문제 아님, 사람이 처리할 항목). 정정(2026-08-24, 후속 확인): 이 판정은 틀렸다 — 막힌 원인은 MaintQ 쪽 자격증명이 아니라 InsuQ가 스킬 자체를 미구현(501 고정)이었던 것이다. 이후 InsuQ 쪽에서 실제 구현이 됐고(단, MaintQ가 D93/D120 인증으로 겨냥하는 정식 Spring 서비스가 아니라 별도 FastAPI 프로토타입 어댑터 :9102에서 동작 — InsuQ 자체 docs/07_BACKLOG.md H9가 이 이원화를 인지 중), MaintQ 기본 타깃이 이미 그 포트라 재검증 가능한 상태다.
🔐 A2A 인증 스킴 교체 (2026-08-24, D120) — Basic → Bearer+X-A2A-Partner-Id. MaintQ가 InsuQ·FinAllQ 레포의 실 인증 필터를 직접 열어 대조한 결과, 양쪽 다 D93이 정한 MAINTQ_A2A_<PARTNER>_CLIENT_ID/_SECRET → Basic 스킴이 아니라 Authorization: Bearer <token> + X-A2A-Partner-Id 자기신고 헤더만 검사하고 있었다(FinAllQ→InsuQ 2차 홉이 이미 이 스킴으로 실 성공 중이었음). MaintQ의 credentials.py·auth_header.py를 실제 스킴에 맞춰 재작성 — <PARTNER>_SERVICE_TOKEN(단일값) 읽기 + Bearer 조립. 단, InsuQ의 lookup-clause가 실제로 동작하는 임시 어댑터(:9102, 위 참고)는 인증 헤더 검증 자체가 없어 이 스킴 일치 여부가 아직 실전 검증되지는 않았다.
🆕 FinAllQ 추가 5스킬 대기 중 (2026-08-24) — MaintQ 발신 트리거 미착수. FinAllQ가 advise-hedge(S6)·advise-financing(S16)·request-settlement(S12)·assess-used-equipment-loan(S13과 별개, 실사용 대출)·advise-replacement-financing(S15, InsuQ claim-insurance 이후 2차 홉 전용) 5종의 계약을 확정하고 자기 쪽 수신 처리를 구현·curl 검증까지 마쳐 공유했다. MaintQ 쪽 발신 트리거(payload 빌더 + 라우터)는 아직 없다 — 이번 시연 범위가 S5·S13/S8 두 개로 확정돼 시연 이후로 미룬 상태다(MaintQ docs/07_BACKLOG.md P34).

> **Q 시리즈 통합** — 제조(MaintQ) · 금융(FinAllQ) · 보험(InsuQ)이 A2A로 연결된다.

>

> 신규 스킬 `lookup-clause` 를 제안한다. 아래 「InsuQ 구현 현황」 참조.
> 근거: `InsuQ/docs/{status,feature-data-map}.html` · `docs/sprints/sprint-8.md` (커밋 `00b74bc`).
>
> ⚠️ **이 문서의 범위는 S5~S8 이다.** S9~S28 은 `Q시리즈_시나리오맵_S1-S18.html` 에,

### 🔑 S5를 여는 데 실제로 필요한 4가지

1. **Agent Card** — `/.well-known/agent-card.json`에 `request-withdrawal` 스킬 선언
2. **`:9001` 얼굴 포트** — 기존 REST 흐름(`POST /transfers`)에 연결하는 **어댑터**. 도메인 재구현이 아니다
3. **`input-required` ↔ 결재함 매핑** — 🟢 *"승인 대기"* 개념이 **이미 도메인에 있다**(`PENDING` + 결재함 화면). Task 상태로 노출만 하면 된다
4. **`request_chain_id`** — 감사 로그에 추가. 🟢 감사 인프라는 append-only로 이미 있고 화이트리스트에 키 하나 등재하는 수준

> 🟢 **2·3·4는 기존 자산 위의 얇은 층이다.** S5가 "구현 중"인 이유는 어려워서가 아니라
> **A2A 인터페이스를 아직 시작하지 않았기 때문**이다.

### FinAllQ가 A2A에 가져오는 검증된 통제 장치

| 장치 | 내용 | A2A에서의 역할 |
|---|---|---|
| **직무 분리 매트릭스** | 판정 축을 곱한 18칸 중 **허용 4칸**. 자기결재 금지, ADMIN은 결재자 아님 | 남의 에이전트가 보낸 요청도 **같은 매트릭스**를 통과해야 한다 |
| **이중 방어** | 규칙(한도) → 모델(FDS) **순서 자체가 통제** | A2A 요청이 모델을 우회할 수 없다 |
| **화이트리스트 차단** | 감사 detail·AI 페이로드는 **등재된 키만** | A2A 페이로드에도 그대로 적용 가능 |
| **append-only 감사** | 성공뿐 아니라 **차단·거부 시도도** 기록 | `request_chain_id`만 얹으면 멀티홉 추적이 된다 |
| **차단기(Fail-soft)** | AI 장애가 코어로 번지지 않음 | **남의 에이전트가 죽어도** 내 코어는 살아야 한다 — 같은 경계가 필요 |
| **테넌트 격리** | 다른 소속에는 *"권한 없음"* 이 아니라 *"안 보임"* | A2A에서 **요청자 회사 밖 리소스가 새지 않는다** |

### 🔑 InsuQ 쪽 A2A 를 여는 데 실제로 필요한 것

1. **Agent Card** — `/.well-known/agent-card.json` 노출 (`TASK-H01`, 미착수).
   초안은 이미 `docs/agent_cards/insuq.json`(v0.1.0-draft)에 있다 — **선언은 있고 구현이 없다.**
2. **`:9002` 얼굴 포트** — ai-engine(:3001)·Spring(:8081) 앞의 **어댑터**. 도메인 재구현 아님.
3. 🔴 **정책 원장(`TASK-E01`)** — 스킬 5종 중 **4종이 이걸 조회한다.** 이게 없으면
   창구를 열어도 `verify-collateral-insurance` 는 빈 응답만 낸다. **여기가 진짜 병목이다.**
4. **`request_chain_id` 로깅** (`TASK-H06`) — 상담이력 DB 영속화가 이미 있어 컬럼 추가 수준.

> ⚠️ **FinAllQ 와 병목이 다르다.** FinAllQ 는 *"레일은 깔렸고 문이 없다"* (2·3·4가 얇은 층)이지만,
> InsuQ 는 **문 + 창고**가 없다. `lookup-clause` 만 예외로 창고가 필요 없다 — 그래서 아래를 제안한다.

### 🆕 신규 스킬 제안 — `lookup-clause` (약관 근거 조회)

- **성격**: 순수 조회. 돈·계약 안 움직임 → 최저 위험.
- **payload**: `{question, domain?: "실손"|"화재재물", product?, requester}`
- **응답**: `{answer, verdict: 높음|낮음|유보, evidence[{policy_part, article_no, clause_no, page, quote}], confirm_required[]}`
- **왜 이걸 먼저 여는가**: 현재 Agent Card 5종은 **전부 정책 원장에 막혀 있다.**
  반면 이 스킬은 **약관 코퍼스만으로 성립**하고, 그 코퍼스·검색·인용·거부는 **이미 측정까지 끝났다**.
  A2A 첫 스킬로서 *"경계를 넘어 요청이 오고 근거와 함께 회신된다"* 를 **가장 싸게 증명**한다.
- **누가 쓰나**: MaintQ 가 *"이 설비 손해가 약관상 뭐라고 돼 있나"*, FinAllQ 가 *"담보 조항 원문"* 을 물을 때.
  S7·S8 의 **부분집합**이라 나중에 그 스킬들이 열리면 내부에서 재사용된다.
- **한계 명시**: 이 스킬은 *"당신 계약이 어떻다"* 를 답하지 않는다 — **약관 일반론만** 답한다.
  계약 단위 답변은 정책 원장이 선 뒤 `verify-collateral-insurance` 가 담당한다.

핵심 차이 한 줄:
**MCP = 에이전트가 자기 도구를 쓴다 / A2A = 완성된 남의 에이전트에게 작업(Task)을 위임한다.**
각 프로젝트는 서로의 내부를 모른 채(블랙박스), Agent Card + Task 생명주기 + HTTP로만 소통한다.

## 0. 통신 그래프 (완전 삼각형)

```
                MaintQ (제조)
               /            \
        S5 출금요청          S7 화재보험
        S6 환헤지상담         (고장이력 연계)
             /                    \
   FinAllQ (은행/증권) ─────────── InsuQ (보험)
                  S8 담보-보험 검증 (멀티홉)
```

세 꼭짓점이 모두 연결된다. 특히 **S8은 세 에이전트를 하나의 요청 흐름에 릴레이**시켜, 단순 쌍 통신을 넘어 다단계 위임(멀티홉)을 증명한다.

| 프로젝트 | 도메인 | 스택(예정) | A2A 얼굴 포트 |
|---|---|---|---|
| MaintQ | 제조 설비보전 | Python + SQLite + Qdrant(or pgvector) | :9000 (오케스트레이터 겸) |
| FinAllQ | 은행·증권 | Java Spring + Python LangGraph + Postgres+pgvector | :9001 |
| InsuQ | 보험 | **Next.js + Java Spring Boot(Java 21) + Python FastAPI** · H2(dev)/**Postgres**(prod) + Qdrant | :9002 |

> ⚠️ **InsuQ 스택 정정 (2026-08-14 실측)**: 이 표는 오래 **"Python + SQLite + Qdrant"** 라고 적고
> 있었고 아래 「인프라 메모」도 *"의도적으로 다른 스택"* 의 근거로 SQLite 를 들었는데, **둘 다 틀렸다.**
> InsuQ 는 실제로 **3층 구조**(브라우저 → Spring :8081 → ai-engine :3001)이고, RDB 는
> **dev H2 인메모리 / prod Postgres**(`application-{dev,prod}.yml` 실측)다. SQLite 는 쓰지 않는다.
> → **"스택이 다른 별개 회사"라는 학습 포인트는 여전히 유효하지만 근거가 바뀐다** — InsuQ 와 FinAllQ 는
> 오히려 **Java Spring + Python** 이라는 같은 골격을 공유하고, 이질성은 **벡터 스토어**
> (Qdrant vs pgvector)와 **프론트 유무**에서 나온다.

## 관통 원칙 — "돈·계약이 움직이는 건 요청/제안 + 사람 승인"

S1~S4의 `create_po_draft`가 **draft만 생성, 확정은 human-in-the-loop**였던 원칙을 A2A 전체로 연장한다.

- AI는 **요청서·제안서·초안까지만** 만든다. 실제 이체·계약 체결·거래 실행은 **사람의 승인 버튼** 뒤에 있다.
- 돈이 실제로 움직이는 작업(S5)은 **승인 계단을 2단**으로 나눈다 (요청 부서 승인 ≠ 집행 부서 승인).
- 조회/상담만 하는 작업(S6·S7·S8)은 실행 위험이 없어 안전하다 — 이쪽부터 구현하면 리스크가 낮다.
- 모든 크로스도메인 요청은 **감사 추적**(요청자·승인자·시각·경로)을 남긴다.

## S5. 발주 승인 → 출금 요청 (2단 승인) — MaintQ → FinAllQ(은행)

- 시작: 정비사 (MaintQ)
- 성격: **작업 위임 + human-in-the-loop** (돈이 움직임 → 최고 주의)
- 전제: S1의 발주서 초안이 보전팀장 승인을 통과한 상태

**흐름:**
1. (MaintQ 내부) 진단 → 부품 특정 → `create_po_draft` → **① 보전팀장 승인** ("이 부품 사는 게 맞나" = 기술 판단)
2. 승인 시 MaintQ가 A2A로 FinAllQ에 **출금 "요청"** 위임 (실행 아님)
   - Task skill: `request-withdrawal`
   - payload: `{po_id, amount, supplier, approved_by, purpose, error_code}`
3. (FinAllQ) 요청 접수 → **기존 FDS(이상거래탐지)로 요청 검사** → `input-required`(승인 대기) 상태 반환
4. **② 재무 담당 승인** ("이 돈 지금 내보내도 되나" = 재무 판단) — 금액 임계값 초과 시 상위 결재 추가
5. 최종 승인 시에만 이체 실행(목업) → 결과를 MaintQ로 회신

**핵심 설계:**
- A2A가 자동으로 하는 건 ①과 ② **사이의 전달**뿐. 돈이 나가는 앞에는 반드시 **사람의 두 번째 승인**.
- "버튼 하나로 자동 이체"가 아니라 **두 부서가 각자 관점에서 승인**해야 나간다.
- 재무부는 없어지지 않는다 — **타이핑(수작업)만 사라지고 판단은 남는다.**

**성공 기준:**
- 재무 승인 없이 이체 실행되는 경우 0건
- 권한 없는 역할의 출금 요청 → 403 차단 100%
- 금액 임계값 초과 시 상위 결재 트리거 100%
- 모든 출금 요청에 승인자·시각 감사 로그 존재 100%

## S6. 환헤지 / 여유자금 운용 상담 — MaintQ → FinAllQ(증권)

- 시작: 공장 재무 담당 (MaintQ)
- 성격: **제안/상담 (실행 X)** → 자동 실행 위험 없음, 안전
- 배경: 제조업은 부품 수입·완제품 수출로 환리스크가 크고, 설비 투자 전까지 유휴 운영자금이 생긴다.

**흐름:**
1. (MaintQ) "다음 분기 달러 결제분 ₩X 규모, 환헤지 방안 상담" 요청
2. A2A로 FinAllQ 증권 에이전트에 위임
   - Task skill: `advise-hedge` (또는 `advise-cash-management`)
   - payload: `{exposure_amount, currency, horizon, risk_tolerance}`
3. (FinAllQ) 시나리오 비교 제안 회신 — 선물환/옵션/무헤지 비교, 여유자금이면 MMF·단기채 등
4. (MaintQ) 제안을 **리포트로 표시** — AI는 여기까지, 실제 상품 가입은 사람이 별도 결정

**성공 기준:**
- 제안만 제시, 임의 실행 0건
- 각 제안에 리스크·비용 명시, 근거 제공
- "투자 자문이 아님" 고지 포함 (상담 성격 유지)

## S7. 화재보험 갱신 (설비 고장이력 연계) — MaintQ → InsuQ(보험)

- 시작: 공장 관리자 (MaintQ)
- 성격: **상담 + 데이터 연계** (두 프로젝트 데이터가 맞물리는 킬러 시나리오)
- 전제: 이미 가입된 공장 화재보험이 존재 (A2A는 기수립 관계 가정 → 신규가입보다 **갱신/증액**)

**흐름:**
1. (MaintQ) 만료 임박 화재보험 갱신 상담 요청 — **지난 1년 설비 사고 이력 첨부**
   - payload: `{building_id, policy_id, incident_history[]}`
2. A2A로 InsuQ 보험 에이전트에 위임
   - Task skill: `advise-policy-renewal`
3. (InsuQ) 약관 RAG + 첨부된 고장이력으로 **리스크 재평가** → 갱신 조건·보험료 제안
   - 사고 이력 많으면 보험료 상향/특약 권고, 적으면 할인 여지 안내
4. (MaintQ) 갱신안 리포트 표시 → 사람이 갱신 결정 (계약 체결은 사람 승인)

**핵심:** MaintQ의 **고장 데이터가 InsuQ의 리스크 평가 근거**가 된다 — 단순 상담을 넘어 데이터가 실제로 흐른다.

**성공 기준:**
- 고장이력이 보험료/조건 산정에 반영됨 (근거 명시)
- 약관 인용률 100% (InsuQ RAG 원칙 유지)
- 계약 체결은 사람 승인 없이 실행 0건

> ✅ **전제 하나가 철회됐다 (2026-08-14, InsuQ EXP-028)**
> 시나리오맵의 S7 설명은 *"공장용 표준 보험 약관 자체를 구하기 어려운 게 확인돼서, 세 프로젝트 중
> 가장 리스크가 큰 부분"* 이라고 적고 있었다. **그 전제가 틀렸다.**
> InsuQ 가 2026-07-31 조사에서 *"공장물건 담보 약관 0종"* 으로 결론냈던 것은 공시실의
> **「일반보험」만 훑고 「장기보험 > 재물」을 안 봤기 때문**이고, 재탐색하니 기업성 재물 3종이
> 거기 있었다 — 「복합구조건물요율적용(**공장물건**) 특별약관」·점포휴업손해 특약 등을 **원문으로 확인**했다.
>
> **현재 상태**: 코퍼스 12종 확보(PDF 24개) → 우선 3종 파싱 **청크 2,214** → 전용 컬렉션
> `insuq_track4` 인덱싱 → 골든셋 **66문항** → 미니 baseline **Hit@5 0.6346** 측정 완료.
> → **S7 의 데이터 리스크는 해소됐다.** 남은 리스크는 데이터가 아니라
> **① 창구 미구현 ② 정책 원장 부재 ③ 고장이력 → 요율 재산정 로직 부재** 셋이다.
> *(교훈: 코퍼스 부재를 결론으로 삼기 전에 탐색 범위부터 문서화해야 한다.)*

## S8. 담보 대출 심사 시 보험 검증 (멀티홉 릴레이) — MaintQ → FinAllQ → InsuQ

- 시작: 공장 경영진 (MaintQ)
- 성격: **멀티홉 위임 + 순수 조회** (돈 안 움직임 → 안전) — **A2A의 하이라이트**
- 증명 패턴: **A가 B를 부르고, B가 다시 C를 부르는 다단계 위임**

**흐름:**
1. (MaintQ) "노후 설비 교체에 5억 필요, 담보 대출 상담" → A2A로 FinAllQ에 위임
2. (FinAllQ) 대출 심사 시작 → 담보 = 공장 건물 → **담보에 유효한 보험이 있는지 InsuQ에 조회** (2차 홉)
   - Task skill: `verify-collateral-insurance`
   - payload: `{building_id, required_coverage, request_chain_id}`  ← 최초 요청 ID를 물려 경로 추적
3. (InsuQ) 해당 건물 보험 조회 → "화재보험 유효, 보장 3억 (대출 5억 대비 부족)" 회신
4. (FinAllQ) 결과 반영 → "보장 부족 → 보험 증액 조건부 승인" 판정 → MaintQ로 회신
5. (MaintQ) "대출 승인됐으나 화재보험 3억→5억 증액 필요" 안내
   → **여기서 S7(보험 증액) 흐름으로 자연 연결**, 이후 승인되면 S5(대출금 집행)로도 연결

**핵심 설계 — 멀티홉 추적:**
- A→B→C 체인에서 `request_chain_id`를 물려 **"누가 시작했고 어떤 경로로 왔는지"** 를 남긴다 (감사·디버깅).
- MaintQ의 시그니처 화면 "실행 trace 시각화"를 **에이전트 경계 너머까지** 확장 → MaintQ→FinAllQ→InsuQ 릴레이를 한 타임라인에 표시.

**성공 기준:**
- 멀티홉 체인이 request_chain_id로 끝까지 추적됨 100%
- 보장액 < 대출금이면 조건부 승인 분기 진입 100%
- 조회만 수행, 이 시나리오에서 돈/계약 실행 0건

## A2A Task 정의 요약 (Agent Card 스킬)

각 프로젝트가 자기 `/.well-known/agent-card.json`에 노출하는 스킬:

| 프로젝트 | 스킬 ID | 성격 | 사용 시나리오 |
|---|---|---|---|
| FinAllQ(은행) | `request-withdrawal` | 요청 접수 (실행 X, 2단 승인) | S5 |
| FinAllQ(증권) | `advise-hedge` / `advise-cash-management` | 제안/상담 | S6 |
| FinAllQ(은행) | `assess-loan` | 대출 심사 (내부에서 S8 2차 홉 트리거) | S8 |
| InsuQ | `advise-policy-renewal` | 상담 + 데이터 연계 | S7 |
| InsuQ | `verify-collateral-insurance` | 순수 조회 | S8 |

**InsuQ 스킬 구현 상태 (2026-08-14 실측)** — `docs/agent_cards/insuq.json` 는 스킬 5종을 선언하지만
레포에는 **A2A 코드가 0건**이다(`a2a`/`agent-card`/`well-known` 검색 결과 0). 선행조건이 스킬마다 다르다:

| 스킬 | 선언 | 구현 | 막고 있는 것 |
|---|---|---|---|
| `advise-policy-renewal` (S7) | ✅ 초안 | ❌ | 창구 + 정책 원장 + 요율 재산정 로직 |
| `verify-collateral-insurance` (S8·S13) | ✅ 초안 | ❌ | 창구 + 🔴 **정책 원장**(조회 대상 자체가 없다) + 비례보상 계산 |
| `notify-asset-change` (S11) | ✅ 초안 | ❌ | 창구 + 정책 원장 + 보험료 정산 |
| `notify-risk-change` (S14) | ✅ 초안 | ❌ | 창구 + 정책 원장 + 요율표 |
| `claim-insurance` (S15) | ✅ 초안 | ❌ | 창구 + 정책 원장 + 보험금 산정 |
| 🆕 `lookup-clause` (제안) | — | 🟢 코어 70% | **창구만** — 약관 코퍼스로 성립, 정책 원장 불필요 |

> 🔴 **패턴이 보인다: 5종 중 4종이 「정책 원장」 한 곳에 걸려 있다.**
> InsuQ 의 A2A 착수 순서는 「쉬운 스킬부터」가 아니라 **`TASK-E01` 정책 원장 → 창구 → 스킬** 이거나,
> 원장을 우회하는 **`lookup-clause` 를 먼저** 여는 것이다.

**공통 규약:**
- 돈/계약 실행 스킬은 즉시 완료하지 않고 `input-required`(사람 승인 대기) 상태를 거친다.
- 모든 Task에 `approved_by`, `request_chain_id`(멀티홉용)를 포함해 감사 추적.
- 인증: OAuth 2.1 (에이전트 간 신뢰 경계) — 실습에선 목업 토큰으로 대체 가능.

## 선택 옵션 (검토했으나 메인에 넣지 않은 대안 시나리오)

필요 시 교체·추가용. 각각 **왜 보류했는지**까지 기록.

### 금융 방향 대안 (S6 자리 후보)

- **[보류] 자사주 매입 / 주가 방어**
  회사가 자사주를 사고팔며 주가를 맞추는 시나리오.
  → **비권장.** AI가 주가를 인위적으로 조정하는 그림은 **시세조종과 경계가 모호**하고, "AI 자동 주식거래"라 실행 위험이 큼. 포트폴리오 시나리오로 부적절.
- **[대안 O] 자금 조달 비교 상담**
  "신규 설비 5억, 대출 vs 리스 vs 회사채 비교" → 증권/IB 에이전트가 시나리오 비교.
  → 안전(상담)하고 현실적. S6를 이걸로 바꾸거나 병렬 추가 가능.

### 은행/증권 ↔ 보험 방향 대안 (S8 자리 후보)

- **[채택됨] 담보 대출 심사 시 보험 검증** → S8 (멀티홉·조회라 최적)
- **[대안 B] 보험금 지급을 위한 계좌 확인/이체**
  InsuQ가 보험금 지급 시 FinAllQ에 수령 계좌 확인·이체 요청.
  → S5의 **반대 방향**이라 대칭은 예쁘지만, 구조가 S5와 겹쳐 학습적 새로움은 적음. 확장 시 좋은 후보.
- **[대안 C] 연금·자산배분 상담 (증권 ↔ 보험)**
  여유자금을 증권/보험(연금)에 배분 설계.
  → 개인 자산관리 성격이라 제조 중심 스토리와 결이 다름. 개인 대상 확장 시 사용.
- **[대안 D] 리스크 데이터 공유 (신용 ↔ 보험)**
  은행 신용평가 ↔ 보험 사고이력 상호 참조.
  → 안전하고 구현 쉬우나 서사가 밋밋. S8의 서브 조회로 흡수 가능.

## 인프라 메모

- **FinAllQ**: Postgres + **pgvector** (관계형 + 금융 약관/리포트 벡터를 한 DB로 통합)
- **InsuQ**: ~~SQLite(일반) + Qdrant(벡터)~~ → **정정(2026-08-14 실측)**:
  **H2 인메모리(dev) / Postgres(prod) + Qdrant(벡터)**, 3층 구조(Next.js → Spring Boot Java 21 → FastAPI).
  **SQLite 는 쓰지 않는다.** 이 항목은 오래 "의도적으로 다른 스택"의 근거로 SQLite 를 들었지만
  실제로는 InsuQ 와 FinAllQ 가 **Java Spring + Python** 골격을 공유한다.
  → "스택이 다른 별개 회사" 라는 학습 포인트는 유효하되 **근거는 벡터 스토어(Qdrant vs pgvector)와
  프론트 유무**로 바꿔 적어야 한다. 원본: `InsuQ/backend/src/main/resources/application-{dev,prod}.yml`.
- **MaintQ**: SQLite 목업 + 벡터스토어 (pgvector 선호 시 교체 가능)
- **배포**: 각 프로젝트를 **Docker 컨테이너로 격리** → "별개 회사" 느낌 + 노트북 관리 용이.
- **포트 감각**: A2A는 **에이전트 얼굴 포트만** 노출(:9000·:9001·:9002). frontend/backend/db는 각 프로젝트 내부 사정이라 밖으로 안 샌다 → 도메인 추가는 **곱셈이 아니라 덧셈**.

**구현 순서 제안 (리스크 낮은 순):**
1. S8·S6·S7 (조회·상담 = 돈 안 움직임) 먼저
2. S5 (출금 = 2단 승인) 마지막 — human-in-the-loop·FDS·감사로그를 정성껏

> ⚠️ **2026-08-14 개정 — 위 순서는 "위험도" 기준이고, 실측하면 「준비도」 순서가 다르다.**
> S8 을 1순위로 둔 것은 *조회라서 안전하다* 는 이유였는데, 실제로 S8 은 **양쪽 다 막혀 있다**
> — FinAllQ 는 대출 심사 도메인이 없고(10%), InsuQ 는 조회할 정책 원장이 없다(15%).
> **가장 안전하면서 동시에 가장 준비된 것은 S5 (FinAllQ 75%)** 인데 그건 돈이 움직인다.
>
> 그래서 실측 기반 순서는 이렇게 갈린다:
> 1. 🆕 **`lookup-clause`** (InsuQ 70%, 선행조건 없음) — *"경계를 넘어 근거와 함께 회신된다"* 를 최저 비용으로 증명
> 2. **S5** (FinAllQ 75%) — 창구 + `input-required` ↔ 결재함 매핑만. 돈이 움직이므로 승인 계단은 정성껏
> 3. **S7** (InsuQ 40%) — 코퍼스는 확보됐고 정책 원장·요율 로직이 남았다
> 4. **S8·S13** (양쪽 10~15%) — 두 도메인의 **없는 기능**이 선행. A2A 하이라이트지만 **가장 늦다**
>
> **"안전한 것"과 "준비된 것"이 다르다** — 순서를 위험도만으로 정하면 착수하자마자 막힌다.

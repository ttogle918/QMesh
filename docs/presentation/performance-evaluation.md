## 🔄 기술 결정 플로우

### 1) 여신(대출) 도메인: RBAC 기반 자동 심사 규칙

**문제:** 신청자 → 자동 심사 규칙 2개 → 사람 승인 필수 구조 필요

**기술 선택:** RBAC (Role-Based Access Control)
- 데이터베이스 레벨에서 직무별 권한 정의
- 자기결재 금지 (신청자 ≠ 결재자)

**구현 전략:**
- **자동 거절 규칙:**
  - LTV(담보비율) > 80% → 자동 거절
  - 신청 금액 > 신용한도 → 자동 거절
- **승인 경로:** 사람이 반드시 검토해야만 승인 가능 (자동 승인 경로 없음)
- **자기결재 방지:** LOAN_006 게이트 검증

**성능 평가:**
- ✅ 신규 테스트 45건 추가
- ✅ 전체 831건 테스트 GREEN (회귀 0건)
- ✅ 쿼리 성능: 4중 JOIN FETCH로 N+1 제거

---

### 2) 페이지네이션: 이중 정렬 키로 동률 처리

**문제:** `ORDER BY createdAt`만 사용 시 동일 시간대 여러 행의 정렬 순서 불정

**기술 선택:** Composite Sorting Key
- `ORDER BY (createdAt DESC, id DESC)` 이중 키
- 완전히 결정론적인 정렬 순서 보장

**구현 전략:**
- 데이터베이스 인덱스: `(createdAt DESC, id DESC)`
- 테스트: 동률 주입 후 100회 반복 실행
- vitest shuffle 상태에서도 안정성 검증

**성능 평가:**
- ✅ 페이지 경계 중복/누락 현상 100% 제거
- ✅ 8건의 버그 해결
- ✅ 반복 실행 신뢰성 100%

---

### 3) 심사 근거 표시: 기존 데이터 재구성 vs 신규 API

**문제:** 사용자가 "왜 심사 결과가 나왔는지" 근거를 보고 싶어함

**기술 선택:** 기존 실데이터 재구성 (신규 API 미추가)
- ❌ 신규 테이블/API 추가 (유지보수 비용 증가)
- ❌ ML/LLM 호출 (외부 의존성)
- ✅ 기존 필드만 응답에 포함 (`coverage_amount`, `ltv`, `credit_limit`)

**구현 전략:**
- 심사 상세 응답에 평가 가중치 필드 추가
- Reviewer 게이트: 데이터 추가 후 검수
- 응답 캐시: loanId 기준으로 불필요한 재조회 방지

**성능 평가:**
- ✅ API 응답 시간 변화 없음 (새 쿼리 추가 없음)
- ✅ 캐시 히트율 증가 (같은 행 재조회 시 API 1회 호출)
- ✅ 테스트 399건 → 407건 (기존 데이터 검증 추가)

---

### 4) 2단계 인증 (2FA): TOTP 자체 구현 vs 외부 API

**문제:** 이체 시스템에서 고액 이체 승인 보안 강화 필요

**기술 선택:** RFC 6238 TOTP 자체 구현
- ❌ 외부 2FA API (Google Authenticator, Twilio) → 의존성↑, 비용↑
- ✅ JDK 표준 암호화만 사용 (HMAC-SHA1)

**구현 전략:**
- TOTP 시드(비밀키)를 사용자마다 고유 생성
- 앱 인증기(Google Authenticator, Microsoft Authenticator 호환)
- 유예 시간: ±30초 (RFC 6238 표준)

**성능 평가:**
- ✅ 외부 API 호출 0회 (응답 시간 ≥100ms 절약)
- ✅ 신규 테스트 24건 (모두 GREEN)
- ✅ 고가용성: 인터넷 끊겨도 작동

---

### 5) 여신↔이체 도메인 연결: 자동 생성 대신 "가드+진입점"만 배선

**문제:** 여신 승인과 이체가 서로 참조하지 않아, 승인된 여신 자금을 실제로 인출할 방법이 없음. 그렇다고 승인 즉시 이체를 자동 생성하면 FDS·2FA·최종 트리거를 사람이 쥐고 있어야 한다는 원칙이 깨짐

**기술 선택:** 연결 테이블 + 서버측 가드, 자동 생성 없음
- ❌ 여신 승인 시 이체 자동 생성 (사람의 최종 트리거 원칙 위반)
- ✅ `transfer_request.loan_id` FK + 전용 정책 클래스(`LoanDisbursementPolicy`)로 출금 시점에만 검증

**구현 전략:**
- 이체 신청(`requestTransfer`) 안에 가드 3줄만 삽입 — 미승인 여신 출금 시도(`LOAN_007`, 409), 잔여 한도 초과(`LOAN_008`, 400)
- 집계 대상 상태(`PENDING·PENDING_2FA·APPROVED·COMPLETED`)는 기존 1일 한도 집계 로직(`DAILY_AGGREGATE_STATUSES`)과 동일한 제외 규칙 재사용
- FDS·2FA는 여신발 이체에도 그대로 적용(우회 경로 0건을 grep으로 고정)
- 프론트는 신청자 본인 화면에서 출금 버튼 클릭 시 `loanId`+잔여금액만 사전채움, 상한 재계산은 하지 않음(서버가 유일한 판정자)

**성능 평가:**
- ✅ 백엔드 신규 테스트 25건, 프론트 신규 테스트 5건 (모두 GREEN)
- ✅ 통합테스트로 FDS 실호출 발생을 Mockito verify로 단정(우회 없음을 테스트로 고정)
- ✅ 실제 브라우저로 신청→결재 대기(자기결재 불가)→승인→완료 전 경로 실증

### 6) A2A `request-withdrawal`: 서비스 계정 부재 발견 → 스코프 재조정

**문제:** A2A로 제출한 출금 요청이 "결재 대기"인지 "TOTP 인증 필요"인지 구분되지 않음. 처음엔 "A2A가 TOTP까지 대신 낸다"로 설계했으나, 계획 단계 실측에서 서비스 계정 자체가 없어 이 스킬이 한 번도 실동작한 적이 없다는 사실이 드러남

**기술 선택:** 서비스 계정을 CORPORATE로 신설 + TOTP 제출 기능은 보류
- ❌ 서비스 계정을 INDIVIDUAL/MANAGER로 만들어 A2A가 TOTP까지 대신 제출 (2FA→1FA 붕괴)
- ✅ CORPORATE 계정 신설 + `pending_action` 필드로 상태만 구분해 폴링에 노출

**구현 전략:**
- `pending_action`: `PENDING→"finance-approval"`, `PENDING_2FA→"totp-verification"`(+`fds_check:"hold"`)
- `CANCELLED→rejected` 매핑 신규 추가(이전엔 미매핑 502 케이스였음)
- `hmac`·`pyotp`·`totp_code` 등 TOTP 관련 심볼 0건을 정적 검사로 회귀 방지 고정

**성능 평가:**
- ✅ 신규 테스트 23건(파라미터화 포함 30회 실행), 기존 100건 포함 130건 GREEN
- ✅ **이 어댑터의 첫 실동작 검증** — 실 서비스 계정으로 신규출금→폴링→MANAGER 실승인→FDS `PENDING_2FA` 전환까지 실제 backend-core로 확인
- ✅ TOTP 대리 제출 기능 보류로 신규 외부 의존성 0, 보안 불변식 유지

## 🏗️ 아키텍처 평가

### ✅ 검증된 기술 선택

**Polyglot Microservices**
- 금융 거래(Spring Boot/Java) ↔ AI 추론(FastAPI/Python) 영역 분리
- 기술 선택의 자유도 확보

**CQRS 패턴**
- 실시간 FDS(Fraud Detection System): Redis(온라인) ↔ PostgreSQL(오프라인) 분리
- 응답 속도 ≥5배 향상

**Agentic AI (LangGraph)**
- 단순 판별에서 벗어나 설명 가능한 AI(XAI) 구현
- 심사자가 "왜"를 이해하고 결정 가능

### ⚠️ 보완 필요 영역 (다음 버전)

- **데이터 동기화 파이프라인:** PostgreSQL → Redis 변경 반영 방식 미명시
- **API Gateway:** 현재 없음, 향후 도입 고려
- **마이크로서비스 간 인증/인가:** mTLS 또는 JWT 전달 방식 미결정
- **Circuit Breaker 패턴:** FastAPI 다운 시 Fail-open/Fail-closed 정책 미명시
- **LangGraph 상태 관리:** Checkpointer 저장소 미결정

## 📐 8가지 절대 원칙

이 프로젝트의 설계 철학으로, 성능과 안정성을 동시에 보장합니다:

### 1️⃣ 존재 이유가 명확해야 함
임시 코드, 주석 처리된 기능, 신규 필드는 반드시 사용 사례가 명시되어야 함

### 2️⃣ JPQL 파라미터 바인딩 필수
SQL 주입 방지 (문자열 연결 금지)

### 3️⃣ 응답·감사 로그에 개인정보 미노출
이메일, 계좌번호, SSN 등 PII는 응답/로그에 기록하지 않음

### 4️⃣ Flyway 마이그레이션 스코프 외 데이터 구조 변경 금지
버전 관리되지 않는 임시 ALTER TABLE 명령 금지

### 5️⃣ 신규 외부 라이브러리·LLM API 도입 금지
architecture_v1.md에 명시된 것만 사용

### 6️⃣ 목록 API는 페이지네이션 필수
전체 데이터 반환 금지, 페이지 크기는 최대 100개

### 7️⃣ 재조회 전 캐시 확인
같은 ID로 다시 조회할 때는 먼저 메모리/로컬 캐시 확인

### 8️⃣ 반복 실행 신뢰성 검증
테스트는 vitest shuffle, 100회 반복, 동률 주입 등으로 우연성 제거

| **권한 제어** | RBAC + 자기결재 금지 | 자동 검증 | 부정 승인 0건 |
| **외부 의존성** | TOTP 자체 구현 | 외부 API 호출 0회 | 응답 시간 ≥100ms 절약 |
| **트랜잭션 안전성** | CAS(Compare-And-Set) | Lost Update 0건 | 동시성 환경 안전 |
| **테스트 자동화** | 신규 테스트 추가 | 백엔드 +45/+24건 | 회귀 0건 |
| **데이터 무결성** | 이중 집계 차단 | DAILY_AGGREGATE_STATUSES | 한도 중복 집계 0건 |
| **도메인 연결** | 여신↔이체 가드 배선(자동생성 없음) | 출금 가드 2종(LOAN_007/008) | 사람의 최종 트리거 원칙 유지 |
| **A2A 실증** | request-withdrawal 첫 실동작 검증 | 서비스 계정 실배선 + 상태 폴링 구분 | 결재대기/TOTP필요 구분 가능 |

## 🎓 assess-loan & coverage_amount 기술 해석

### assess-loan 스킬의 역할

- **어디에:** A2A(API-to-API) 시나리오 중 S8 담보 대출 상담
- **무엇을:** 담보가 있는 대출을 심사하고 평가액(coverage_amount)을 계산
- **왜:** 담보 대출의 위험도를 정량화하기 위해 (LTV = 대출금 ÷ 담보평가액 합계)

### coverage_amount 성능 특성

| 항목 | 기술 특성 | 성능 영향 |
|------|----------|----------|
| 데이터 출처 | collateral 테이블 appraised_value | JOIN 1회 필수 |
| 집계 | 담보 여러 개 합산 | SUM(appraised_value) GROUP BY loanId |
| 계산 | LTV = loanAmount ÷ coverage_amount | DB 계산 권장 |
| 캐싱 | 담보 추가/삭제 시만 무효화 | 쿼리 ≥1회 절약 |
| 테스트 | coverage_amount = 0 (무담보) 케이스 | Division by zero 방지 |

## 🔮 향후 개선 가능 영역

### 1. 데이터 동기화 파이프라인 명문화
**현재:** PostgreSQL이 진실의 원천(SSOT), Redis는 캐시
**개선:** PostgreSQL 변경 시 → RabbitMQ/Kafka → Redis 동기화 자동화

### 2. API Gateway 도입
**현재:** 클라이언트가 각 마이크로서비스로 직접 호출
**개선:** Kong/Nginx 기반 단일 진입점 + 요청 검증 + 속도 제한

### 3. Circuit Breaker & Retry 정책 명시
**현재:** FastAPI 다운 시 시나리오 자체 실패
**개선:** Resilience4j로 Fail-open(기본값 반환) vs Fail-closed(거절) 선택 가능

### 4. LangGraph 상태 저장소 선택
**현재:** 기본값(메모리, 단일 인스턴스 전용)
**개선:** PostgreSQL Checkpointer로 확장성 확보

### 5. 분산 추적(Distributed Tracing)
**현재:** 요청 흐름을 로그로만 추적
**개선:** OpenTelemetry + Jaeger로 마이크로서비스 간 지연 시간 시각화

### 6. 벤치마크 자동화
**현재:** 수동 성능 테스트
**개선:** JMH(Java), Locust(Python)로 지속적 성능 모니터링

### 7. 실시간 모니터링 대시보드
**현재:** 사후 로그 분석
**개선:** Prometheus + Grafana로 응답 시간, 에러율, 캐시 히트율 실시간 감시

## 0. 먼저 — 이 문서는 두 층을 담고 있다

조사 과정에서 **QMesh와 무관한 FinAllQ 자체의 미완성**이 함께 드러났다. 파일명이
`A2A_IDENTITY`라 전부 A2A 얘기로 읽히기 쉬우므로 여기서 분리해둔다.

| 층 | 해당 절 | QMesh가 필요한가 |
|---|---|---|
| **① FinAllQ 단독 문제** | §2.3 company 시한폭탄 · §2.5 온보딩 모델 · §2.6 위임 체인 · **§2.7 결정 3건** | ❌ **QMesh가 영원히 없어도 필요하다** |
| **② QMesh 전제 문제** | §1.4 외부 식별자 · §1.5 여신·정산 도메인 · §1.6 market_context 원천 · §3 머신 신원/파트너 자격증명 · **§3.3 연결 2단계 모델** | ✅ A2A 착수 시점에 의미가 생긴다 |

**층 ①이 왜 A2A와 무관하게 필요한가** — Sprint 8이 기업 결재 라인(CORPORATE 모드·MANAGER
결재·자기결재 금지·테넌트 격리)을 만들었고 Sprint 9가 관리자 고객 관리 화면까지 붙였는데,
**기업 고객을 등록하는 경로가 V14 SQL 시드밖에 없다.** 기업 기능은 완성됐으나 기업 고객을
만들 수 없는 상태다(유일한 CORPORATE가 데모 시드 `(주)한빛상사` 1건인 이유).

**의존 방향은 단방향이다** — 층 ①은 층 ② 없이 단독으로 가치가 있지만, 층 ②는 층 ① 없이
성립하지 않는다(파트너를 "company에 붙는 principal"로 표현하려면 그 company가 제대로
만들어지는 경로가 먼저 있어야 한다). 착수 순서가 강제된다: **① → ②**.

§4의 판단표 "A2A 없이도 문제인가" 열이 이 구분과 같은 축이다.

### 1.4 사업자번호를 파트너 식별자로 쓸 때의 문제 (4가지)

1. **공개정보다.** 국세청·계약서·세금계산서에 다 있다. 식별자(identifier)로는 되지만
   **인증자(authenticator)로는 절대 안 된다.** payload에 사업자번호만 받고 처리하면
   "번호만 알면 남의 회사 출금을 요청"할 수 있다.
2. **1:N을 표현하지 못한다.** 한 회사가 MaintQ 외에 다른 시스템·다른 에이전트를
   동시에 물릴 수 있다. 파트너 시스템별 권한·한도·폐기(revoke)를 따로 관리하려면
   회사당 1개인 사업자번호로는 부족하다.
3. **개인 고객은 NULL이다.** `ck_company_brn_by_type`이 INDIVIDUAL의 NULL을 강제하므로
   개인 고객 대상 A2A는 이 키로 아예 표현할 수 없다.
4. **변한다.** 폐업·법인 전환·합병 시 번호가 바뀐다. 여신 이력의 앵커로는 불안정하다.

→ **필요한 것**: 별도의 발급형 식별자. 예 `external_partner_id`(불투명 문자열, 회사당 N개,
개별 폐기 가능). 사업자번호는 **온보딩 시 대조용**으로 남기고, 런타임 식별은 발급 ID가 맡는
분리가 정석이다.

### 2.2 company row는 회원가입의 "부작용"으로 생긴다

`AuthService.signUp()` (`service/AuthService.java:35-41`)

```java

        .orElseGet(() -> {

            newCompany.setCompanyName("K-FinBank");
```

의도는 "모든 가입자를 기본 회사(id=1)에 붙인다"였다. `Company` 엔티티의 기본값이

V14 시드(`(주)한빛상사`)가 SQL로 직접 넣은 것이다. 관리자 API도 조회 전용이다 —
`AdminController`에 `GET /customers`, `GET /customers/{id}`는 있지만 **생성·수정 엔드포인트가
없다**(그 외 엔드포인트는 역할 부여·규제룰뿐).

### 2.5 온보딩 모델 — 초대 기반 (2026-08-13 논의)

제안: *"새 company를 만드는 대신, company 담당자가 소속 직원 계정을 발급한다. 기업 재무팀만
그 계정으로 접속하면 되지 않나?"*

#### ✅ 채택 — 담당자 발급(초대) 모델

**스키마가 이미 이 모델을 전제하고 있다.** `company 1:N users`(V1) + `UserRole{USER, MANAGER}` +
V14 시드의 구성(company 1개에 MANAGER 1 + USER 1)이 정확히 그 모양이다.
**없는 것은 모델이 아니라 그 모델을 만드는 API**다.

온보딩 경로를 고객 유형별로 갈라야 한다:

| 유형 | 경로 | company 생성 | 계정 생성 |
|---|---|---|---|
| 개인(INDIVIDUAL) | self-signup (현행 `/auth/signup`) | 본인용 1행 | 본인 1개 |
| 기업(CORPORATE) | 담당자 등록 → 직원 초대 | **등록 절차에서 1회만** | 담당자가 N개 발급 |

기업 경로에 필요한 것: 고객 등록 API(회사명·사업자번호·유형, ADMIN 또는 온보딩 심사) →
초대/계정 발급 API(담당자 = 해당 company의 MANAGER, 소속 company에 한정) → 역할 지정
(`AdminController`의 역할 부여는 ADMIN 전용이므로 **기업 담당자용 별도 표면**이 필요하다.
MANAGER는 `/api/v1/admin/**`에 접근할 수 없다 — `UserRole` 주석의 SoD 원칙).

#### 🔴 기각 — company 계정 공유(한 계정 동시 접속)

세 곳이 동시에 무너진다.

1. **이체 기능이 영구 차단된다.** `ApprovalPolicy.java:72`가
   `isSelf = requester.userId == approver.userId`로 자기결재를 판정하고, :84에서
   CORPORATE + isSelf를 `TRANSFER_006`으로 거부한다. 계정이 하나면 **isSelf가 항상 true** —
   기업 이체가 100% 막힌다. 우회가 아니라 기능 소멸이다.
2. **감사 로그가 무의미해진다.** `audit_log.actor_user_id`(V7:3)가 전부 같은 값이 되어
   "누가 이 이체를 실행했나"에 답할 수 없다. 금융 서비스에서 양보 대상이 아니다.
3. **애초에 동시 접속이 안 된다.** Refresh 토큰이 Redis `RT:{email}` **단일 키**라
   (`AuthService.java:74`), 두 번째 사람이 로그인하면 첫 번째 세션이 끊긴다.
   공유 계정은 "동시 접속"이 아니라 "서로 쫓아내기"가 된다.

#### "재무팀만 쓰면 된다"에 대하여

사용자 모수가 소수라는 관찰은 **맞다**. 다만 그것이 *계정 1개*를 뜻하지는 않는다 —
**회사 1개 : 계정 N개(사람 수만큼)**가 맞고, 재무팀 3명이면 MANAGER 1 + USER 2다.
사람 수가 적다는 사실이 주는 실제 이점은 다른 데 있다: **초대 발급 API를 무겁게 만들 필요가
없다**(대량 SCIM 프로비저닝·SSO 연동 불필요, 담당자 수동 발급으로 충분).

### 2.6 신뢰 앵커와 위임 체인 — 이 모델이 은행에 주는 것

초대 모델의 본질은 **"심사를 회사당 1회만 하고, 그 뒤의 신원확인 책임을 회사에 위임한다"**이다.
실제 기업 인터넷뱅킹의 **마스터 ID / 서브 ID** 구조가 정확히 이것이다.

```
[1회, 무겁다]  기업 실재 확인(사업자등록증명원·법인등기부·대표자 확인)
                    → 신뢰 앵커 1개 = 마스터 계정
                              ↓ 위임
[N회, 가볍다]  마스터가 직원 계정 발급 · 권한/한도 부여 · 퇴사자 폐기
```

#### 은행이 얻는 것

1. **KYB(기업실사)가 O(회사) 이지 O(직원)이 아니다.** 직원이 100명이어도 서류 심사는 1회다.
2. **인사 정보를 은행이 추적하지 않아도 된다.** "누가 재무팀인지·누가 어제 퇴사했는지"는
   은행이 알 수 없고 회사만 안다. 그 정보를 가진 쪽에 권한을 넘기는 게 정확하다.
3. **책임 경계가 선명해진다.** 은행은 *"이 회사가 실재하고 이 사람이 대표한다"*까지,
   회사는 *"내부에서 누가 무엇을 할 수 있다"*까지. 사고 시 귀책 판정이 가능해진다.

#### 대가로 생기는 문제 (설계에서 답해야 함)

1. 🔴 **마스터 승계.** 첫 담당자가 사실상 "회사 돈을 움직일 사람을 정하는 권한"을 갖는다.
   그 사람이 퇴사·사고를 당하면? 승계 절차가 없으면 회사가 잠긴다. 실무에서 가장 골치 아픈
   지점이며, 복구 경로는 결국 다시 무거운 서류 절차(= 앵커 재설정)다.
2. ⚠️ **발급 권한 ≠ 결재 권한.** 마스터가 계정 발급과 이체 결재를 겸하면
   "자기가 만든 계정으로 요청 → 자기가 결재"가 가능해져 SoD가 형해화된다.
   **현재 `UserRole`에는 발급자 역할이 없다**(USER·MANAGER·ADMIN 3개뿐) —
   MANAGER에 발급을 겸하게 할지, 별도 역할을 둘지가 미결이다.
   역할 추가는 `docs/plan.md`에 없는 변경이므로 절대 원칙 5에 따라 명시적 결정이 필요하다.
3. ⚠️ **위임의 상한.** 회사가 위임받은 권한으로 무제한 계정을 찍을 수 있으면 은행의
   리스크 통제가 사라진다. 회사 단위 한도(계정 수·이체 한도)는 은행이 쥐어야 한다.

#### 그리고 이것이 A2A의 확장 경로다

위임 체인이 서면 외부 파트너를 **"같은 company를 가리키는 또 하나의 principal"**로 표현할 수
있다 — 사람 계정(user) 옆에 머신 계정(파트너 자격증명)이 나란히 붙는 형태.
§3.2의 위임 테이블이 이 자리에 들어간다.

**핵심 이점: 은행이 MaintQ를 직접 심사하지 않아도 된다.** *회사가 자기 파트너를 등록*하는
구조가 되므로, 파트너사가 늘어날 때 은행의 심사 부담이 선형으로 늘지 않는다
(FinAllQ가 파트너사를 일일이 온보딩하는 구조는 확장되지 않는다).

단 조건이 붙는다 — **회사가 외부 시스템에 부여할 수 있는 권한의 상한은 은행이 정한다.**
"MaintQ에 출금 권한을 준다"를 회사 단독으로 무제한 결정하게 두면 위 #3이 A2A 규모로
확대된다. 파트너 자격증명에는 최소한 **한도·허용 작업 종류·유효기간**이 함께 발급돼야 한다.

부수 효과로 §5-4의 스키마 충돌(`transfer_request.requester_user_id` NOT NULL인데 외부 요청에
요청자 user가 없다)에 선택지가 생긴다 — 파트너를 **서비스 계정 user row**로 만들면 FK가
충족된다. 다만 그러면 사람/머신이 같은 테이블에 섞여 RBAC 판정이 오염될 위험이 있다
(`ApprovalPolicy`가 role만 보고 판정한다). `principal_type` 구분 컬럼을 두든 별도 테이블을
두든, **결재 라인이 머신 주체를 사람으로 오인하지 않게** 하는 것이 조건이다.

### 2.7 미결 3건의 결정 (2026-08-13)

§2.6이 남긴 세 문제를 결정 가능한 수준까지 좁힌다. **셋 다 기존 코드에 선례가 있다.**

#### ① 마스터 승계 — `AdminUserService`의 lockout 가드를 회사 단위로 확장

선례가 이미 있다. `AdminUserService.java:40-47`이 "마지막 ADMIN 소실"을 막는다:

```java
if (previous == UserRole.ADMIN && newRole != UserRole.ADMIN) {
    if (userRepository.countByRole(UserRole.ADMIN) <= 1) throw new LastAdminRemovalException(...);
    if (target.getEmail().equals(actorEmail))            throw new LastAdminRemovalException(...);
}
```

🔑 **:37-39 주석의 교훈을 그대로 가져온다** — 불변식을 `newRole == USER` 같은 **열거식으로 쓰면
새 role이 추가될 때마다 가드가 다시 뚫린다**(TASK-108에서 실제로 겪었다). 반드시
*"발급 권한에서 벗어나는가"* 형태로 쓴다.

**결정: 2단 방어.**

| 단 | 내용 | 커버 범위 |
|---|---|---|
| **① 소프트 가드** | 회사의 마지막 발급자는 강등·삭제 불가. 본인 강등 불가 | 실수·오조작 |
| **② 하드 복구** | ADMIN(은행)이 서류 심사 후 발급자를 강제 지정 = **앵커 재설정** | 퇴사·사망·계정 분실 |

②가 **반드시 있어야 한다.** ①만 두면 담당자가 퇴사한 순간 회사가 영구히 잠기고, 시스템
내부에는 그걸 풀 수단이 없다. ADMIN 전용 경로는 이미 `AdminController`(`@PreAuthorize("hasRole('ADMIN')")`)에
자리가 있다.

ADMIN 가드와의 차이: **scope가 전역이 아니라 회사별**이다 — `countByRole(ADMIN)`이 아니라
`countByCompanyIdAndRole(companyId, …)`가 필요하다.

#### ② 발급자 역할 — 직교 플래그(권장), 그리고 남는 위험을 정직하게 기록

🔴 **먼저 위협을 정확히 특정한다.** 발급과 결재를 겸하면 다음이 성립한다:

```
MANAGER가 유령 USER 계정 발급 → 유령 명의로 이체 요청 → MANAGER 본인이 결재 → 통과
```

`ApprovalPolicy:72`의 자기결재 방지는 `requester.userId == approver.userId` 비교라
**유령은 다른 user_id이므로 isSelf=false로 통과한다.** SoD가 실질적으로 뚫린다.

| 옵션 | 방식 | 평가 |
|---|---|---|
| **A** | MANAGER가 발급 겸임 | 스키마·`plan.md` 무변경(가장 쌈). 위 공격에 그대로 노출 |
| **B** | 새 role `COMPANY_ADMIN` | SoD는 확실하나 **`users.role`이 단일 컬럼이라 겸직 불가** — 재무팀 3명이면 발급자 1명이 결재자에서 빠진다. 소규모 고객에 과한 부담 |
| **C** ✅ | 직교 플래그 `users.can_invite BOOLEAN` | role 열거를 안 건드려 기존 판정(`== MANAGER` 5곳) 전부 무영향. 겸직 허용/금지를 **데이터로** 표현 → 회사 규모별 선택 가능. V15 한 컬럼 |

**권장: C.** role 열거 변경은 `ApprovalPolicy`·`TransferQueryService`·`CustomUserDetailsService`·
`AuditAspect` 등 role을 읽는 모든 지점의 재검토를 부르지만, 직교 플래그는 그 표면을 건드리지 않는다.

**C에 반드시 따라붙는 보완 통제 3가지** (C 단독으로는 위 공격이 안 막힌다):

1. **초대로 만들 수 있는 역할은 `USER`로 고정.** MANAGER 승격은 초대 경로 밖에 둔다 —
   유령이 *결재자*가 되는 경로를 끊는다.
2. **계정 발급을 감사 로그 필수 기록.** `AuditAspect` 기존 인프라를 그대로 쓴다.
3. **회사별 계정 수 상한을 은행이 보유**(§2.6 대가 #3의 구체화).

⚠️ **잔여 위험 (정직하게 남긴다).** 위 셋을 다 해도 *"유령 USER 요청 → MANAGER 결재"*는
막히지 않는다. 이는 **결재자가 1명뿐인 구조의 근본 한계**이며, 진짜 해법은 둘 중 하나다 —
결재자 2인 이상 강제, 또는 **신규 계정의 첫 이체를 FDS로 포착**(`fds_rule` 인프라가 이미 있다).
이 결정은 본 문서 범위 밖이며 착수 시점에 판단한다.

#### ③ 초대 토큰 — Redis, `RT:{email}` 선례를 그대로 따른다

| 항목 | 결정 | 근거 |
|---|---|---|
| 저장소 | Redis (`RedisService` 기존 4개 메서드로 충분) | 새 의존성 0 (절대 원칙 5) |
| 키 | `INVITE:{email}` **단일 키** | `RT:{email}` 선례와 동형. **재초대가 이전 초대를 자동 무효화**한다 |
| 값 | `{companyId, role, invitedByUserId, tokenHash, issuedAt}` | — |
| 토큰 | `SecureRandom` 256bit → URL-safe Base64 | 추측 불가 |
| 🔴 저장 형태 | **평문 금지 — 해시로 저장** | 비밀번호 관례와 동일. Redis 유출 시 초대 탈취 방어 |
| 수락 | `email` + `token` 동시 제출 → 해시 비교 | 단일 키 구조에서 토큰 소지 증명 |
| TTL | 72시간 (Redis 자동 만료) | 별도 만료 배치 불필요 |
| 폐기 | 담당자 취소 = `deleteValue` · 수락 성공 시 즉시 삭제(1회성) | — |

> 💡 `RT:{email}` 단일 키의 알려진 부작용(재로그인 시 이전 세션 끊김, CLAUDE.md)이
> **여기서는 오히려 이점이다** — 재초대가 이전 초대장을 무효화하는 것이 올바른 동작이다.

🔴 **초대 수락 전에는 `users` row를 만들지 않는다.** 미리 만들면 미수락 계정이 company에
쌓여 §2.3과 같은 유령 행 문제가 그대로 재발한다. 계정은 **수락 시점에 생성**한다.

## 3. 조사 ③ — 현재 인증 구조 위에서 외부 신원을 어떻게 실을까

### 3.1 지금 구조의 실측

**JWT 클레임** (`security/JwtTokenProvider.java:44-56`)

```java
Claims claims = Jwts.claims().setSubject(email);   // sub = 이메일
claims.put("role", roleStr);                        // role = USER | MANAGER | ADMIN
// 그 외 클레임 없음 — company_id 없음, issuer/audience 없음
```

- Access Token: HS256 대칭키, 1시간, 메모리 보관
- Refresh Token: HttpOnly 쿠키 + Redis `RT:{email}` **단일 키**(재로그인 시 이전 세션 무효)
- 인가: `anyRequest().authenticated()` + `@PreAuthorize("hasRole('ADMIN')")` 등 메서드 시큐리티

**회사 스코프는 토큰이 아니라 DB 재조회로 잡는다.** `JwtTokenProvider.getAuthentication()`이
매 요청 `email → UserDetails`를 로드하고, 서비스 계층이 `user.getCompany()`로 테넌트를 얻는다.
Sprint 9 Stage 2에서 이걸 쿼리 술어까지 내렸다 —
`TransferRequestRepository`의 결재함 쿼리는 `c.companyId = :approverCompanyId`와
`customerType = CORPORATE`를 WHERE에 박는다.

> 시사점: **테넌트 격리의 뼈대는 이미 있다.** 없는 것은 "그 companyId를
> *사람이 아닌 호출자*로부터 얻는 방법"이다.

**MCP Hub의 신원 처리** (`mcp/hub/app/clients/backend_client.py:56-70`)

```
inbound  X-User-Authorization: Bearer <t>
outbound Authorization:        Bearer <t>       # 그대로 재구성, 파싱·로깅 안 함
auth_header is None → 즉시 401 (백엔드 호출조차 안 함)
```

**Hub는 자기 신원이 없다.** 사용자 토큰을 그대로 위임(delegation)해 백엔드를 부른다.
서비스 계정도, 클라이언트 자격증명도, 서명 검증도 없다.
→ **현재 FinAllQ 전체에 "머신 신원(machine identity)" 개념이 0이다.** A2A의 진짜 공백은
company 매핑보다 이쪽이다. MaintQ는 사용자 토큰을 가질 수 없다.

### 3.2 두 옵션 검토

#### 옵션 A — 토큰 기반 (JWT에 company_id 포함)

**방식**: 파트너에게 자격증명을 발급하고, 발급된 토큰의 클레임에 `company_id`(또는
`partner_id`)를 실어 보낸다. 서버는 토큰 클레임만으로 테넌트를 결정한다.

| | |
|---|---|
| ✅ | **위조 불가**. 서명이 신원을 보증하므로, 요청자가 자기 회사를 스스로 주장할 수 없다 |
| ✅ | 폐기(revoke)가 자격증명 단위로 깔끔하다 — 사고 시 그 파트너만 끊는다 |
| ✅ | 감사 로그에 "누가"가 자동으로 남는다(`AuditLog`에 actor를 실을 근거가 생긴다) |
| ✅ | 기존 `JwtAuthenticationFilter` 파이프라인을 재사용 — 구조 변경이 작다 |
| ⚠️ | **`getAuthentication()`이 email → UserDetails 로드를 전제한다.** 사람 계정이 아닌 주체를 태우려면 이 지점이 갈라져야 한다(가짜 User row를 만드는 우회는 RBAC를 오염시킨다 — 권장하지 않는다) |
| ⚠️ | HS256 **대칭키**다. 외부 회사에 발급하는 토큰은 비대칭(RS256/ES256)이 정석 — 검증자와 발행자를 분리해야 파트너가 늘어도 키가 안 샌다. `app.jwt.secret` 단일 키 구조 변경이 필요 |
| ⚠️ | `iss`/`aud`/`jti` 클레임이 없어 재사용·교차사용 방어가 없다 |
| ⚠️ | Refresh가 `RT:{email}` 단일 키 — **머신 주체에는 의미 구조가 안 맞는다**(파트너는 재로그인 개념이 없고 장기 자격증명 + 단기 액세스 토큰이 맞다) |

#### 옵션 B — payload 명시 식별자 (요청 본문에 사업자번호/파트너ID)

**방식**: 요청 body에 `{"businessRegistrationNumber": "1234567896", ...}`를 받아
company를 조회한다.

| | |
|---|---|
| ✅ | 구현이 가장 작다. `findByBusinessRegistrationNumber` 하나 + 기존 유니크 인덱스로 끝 |
| ✅ | 대리 요청(A사가 B사 건을 위임받아 처리)을 자연스럽게 표현한다 |
| ✅ | 토큰 인프라를 안 건드린다 |
| 🔴 | **단독으로는 인증이 아니다.** 사업자번호는 공개정보 — 이것만으로 처리하면 번호를 아는 누구나 남의 회사 여신·출금을 건드린다. **절대 원칙 3(민감정보)·RBAC 취지 정면 위반** |
| 🔴 | 열거 공격 표면. 유효한 번호를 넣어보며 고객 존재 여부를 탐지할 수 있다 |
| ⚠️ | 검증 책임이 엔드포인트마다 흩어진다 — 한 곳이라도 빠뜨리면 그게 구멍이다 |

#### 🔑 정정 — 이 둘은 배타적 선택지가 아니다

두 옵션은 **서로 다른 축**을 답한다.

- 토큰이 답하는 것 = **actor**("누가 호출했나") → 인증
- payload가 답하는 것 = **subject**("누구 건을 처리하나") → 대상 지정

A2A는 actor ≠ subject가 될 수 있는 구조다(MaintQ가 자기 건을 요청하면 같지만,
플랫폼 역할을 하면 다르다). 따라서 실무 정답은 **A + B의 조합**이다:

```
파트너 자격증명(client credentials) → 서명된 액세스 토큰(actor = partner_id)
        +
요청 payload의 대상 식별자(subject = company)
        +
서버가 보유한 위임 테이블: partner_id → 다룰 수 있는 company_id 집합
```

payload의 subject는 **신원이 아니라 파라미터**로 취급하고, 서버가 "이 actor가 이 subject를
다룰 권한이 있는가"를 위임 테이블로 검사한다. 이러면 옵션 B의 🔴 두 개가 사라지고
옵션 A의 대리 요청 한계도 사라진다.

이 형태는 기존 구조와도 맞는다 — 지금 결재함 쿼리가 `companyId`를 WHERE 술어로 내리는
패턴(Sprint 9 Stage 2)이 그대로 **"허용된 company 집합"** 술어로 확장된다.

### 3.3 연결 2단계 모델 — QMesh 확정 사항 반영 (2026-08-13)

QMesh가 §3.2의 "옵션 A+B 조합"과 §2.5의 초대 모델을 그대로 채택하면서, **연결 자체를 2단계로
분리**하는 결정을 새로 확정했다. 이 절은 그 결정이 이 레포에 요구하는 것을 정리한다.

```
[1단계] 회사 간 연결 승인          — 사람이 사람을 승인한다
   우리 ADMIN  ←승인→  MaintQ 담당자
        └─ 승인 시점에 파트너 자격증명(client credentials) 발급
                 │
[2단계] 에이전트 간 통신           — 기계가 기계를 부른다
   MaintQ 에이전트 ──자격증명→ 액세스 토큰 ──→ S5·S6·S8·S12·S13·S15·S16 호출
```

**왜 이 분리가 옳은가** — §2.6의 신뢰 앵커 논리가 회사 간 관계로 한 단 올라간 형태다.
사람이 하는 무거운 판단(이 회사와 거래할 것인가)을 1회로 끝내고, 그 뒤의 반복 호출은
기계가 자격증명으로 처리한다. 앵커가 사람이라는 성질이 유지된다.

#### 🔑 순서 정정 — 연결 승인은 #126의 앞단이 아니라 뒷단이다

착수 검토 중 "연결 승인이 기업 고객 등록(#126) 앞에 와야 한다"는 의견이 있었으나,
**뒷단이 맞다**. MaintQ에 대출·출금을 제공하려면 그 회사가 먼저 `company`(CORPORATE)
레코드로 존재해야 한다 — 신용한도·계좌·여신이 전부 거기 매달린다. 등록 없이 연결부터 하면
"누구와 연결했는지"를 매달 곳이 없다.

```
기업 고객 등록(#126, 층 ①)  →  연결 승인(#131, 층 ②)  →  자격증명 발급(#131)
```

#### 자격증명에 함께 실려야 하는 것 (§2.6 "위임 상한은 은행이 정한다"의 구체화)

자격증명을 "인증 수단"으로만 보면 §2.6이 경고한 위임 남용이 A2A 규모로 커진다.
발급 시점에 **상한을 함께 새긴다**:

| 항목 | 내용 | 왜 필요한가 |
|---|---|---|
| **허용 작업 종류** | 아래 **3단계 위험도 등급** | 🔴 상담과 자금이동은 위험도가 다르다. 한 덩어리로 주면 상담용 연결이 출금 권한을 갖는다 |
| **한도** | 금액·건수 | ③ 등급에 필수. 무제한 위임은 통제가 아니다 |
| **유효기간** | 만료 시각 | 무기한 발급 금지 — 폐기를 잊어도 시간이 닫는다 |

#### 허용 작업의 3단계 등급 (QMesh 합의, 2026-08-13)

스킬을 평면 목록으로 두면 위험도 차이가 사라진다. **등급 단위로 부여한다**:

| 등급 | 스킬 | 성격 |
|---|---|---|
| **① 조회/상담** | S6 `advise-hedge` · S16 `advise-financing` · S15 `advise-replacement-financing` | 실행 없음 |
| **② 심사** | S8 `assess-loan` · S13 `assess-used-equipment-loan` | 결과가 **조건부 승인일 뿐 실행이 아니다** |
| **③ 자금이동** | S5 `request-withdrawal` · S12 `request-settlement` | 🔴 input-required **2단 승인 필수** |

#### S15의 "직접 진입 금지" — 스코프가 아니라 체인 연속성 문제다

`advise-replacement-financing`은 직접 진입이 없고 InsuQ `claim-insurance` 응답 이후 2차 홉으로만
호출된다. **체크박스형 허용 목록으로는 이 성질을 표현할 수 없다** — 목록에 넣으면 직접 호출도
열리고, 빼면 정당한 2차 홉까지 막힌다.

🔑 **해법(QMesh 합의)**: 자격증명 스코프와 분리해 **서버 로직으로 검증한다.** 요청에 필수로 실리는
`request_chain_id`를 받아 *"이 chain_id로 시작된 InsuQ `claim-insurance`가 실제로 존재하고
완료됐는가"*를 FinAllQ가 확인한다. 즉 **"무엇을 부를 수 있는가"(스코프)가 아니라 "이 호출이
정당한 맥락에서 왔는가"(연속성)의 문제**다.

> ⚠️ 이 검증은 InsuQ 조회 또는 QMesh 체인 상태 조회를 수반한다 — **외부 호출이므로 절대 원칙 8
> (캐싱) 대상**이고, 조회 실패 시 거절할지 보류할지의 정책을 함께 정해야 한다. 131번 체크리스트에
> 반영했다.

#### 이 레포에 없는 것 (131번으로 등재)

- 발급형 파트너 식별자(`external_partner_id`) — `company_id`를 외부에 그대로 노출하면
  내부 시퀀스가 열거 표면이 된다(§1.1)

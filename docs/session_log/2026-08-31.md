## 2. 스택 기동 — 촬영보다 오래 걸렸다

기동 과정에서 걸린 것들. **전부 「선언과 실제가 다르다」 형태다.**

### ① InsuQ Spring이 낡은 빌드로 돌고 있었다 (토큰 없이 확정)

`insuq-af`가 "토큰이 있으면 curl로 찍어봐 달라"고 했지만 **시각 대조로 토큰 없이 확정**했다:

| 항목 | 시각 |
|---|---|
| `lookup-clause` Spring 구현 커밋 | 09:37:44 |
| **java 프로세스 기동** | **10:39:19** |
| 빌드 산출물 `V9__grant...sql` | 10:50:52 |

**프로세스가 현재 빌드보다 11분 먼저 떴다.** V9 파일은 프로세스 기동 시점에 존재하지도
않았으므로 Flyway가 적용했을 리 없다 → grant 없음 → 촬영하면 403이 났을 것이다.

### 🔴 그런데 그 판정 기준 자체가 틀렸다 (내 오류)

`insuq-af`가 재기동 후 알려줬다 — **dev 프로파일 + H2 인메모리라 Flyway가 아예 안 돈다.**
V9는 Postgres 경로이고 dev에서는 `CustomerSeeder`가 grant를 만든다. 기동 로그에
`회사 그랜트 7건`이 찍힌다.

**나는 「`Migrating schema ... version 9` 줄을 확인하라」는 기준을 두 세션에 퍼뜨렸다.**
그 줄은 이 구성에서 원리적으로 안 나온다. 결과적으로 200이 나와 실해는 없었지만 **없는
신호를 찾으라고 한 것**이다. `insuq-af`가 트러블슈팅 문서에 못박았다.

### ② MaintQ 프론트가 백엔드를 못 찾았다

```
OPTIONS http://localhost:8897/api/po → 503
frontend/.env: NEXT_PUBLIC_API_BASE=http://localhost:8897
포트 실측:      8897 없음 · 8000 LISTEN
```
프론트는 도커 판 백엔드를 보는데 백엔드는 맨 프로세스로 `:8000`에 떠 있었다.
**API 직접 호출은 통했고 화면만 안 됐다** — 이 패턴이 오늘 반복해서 나온다.

### ③ InsuQ compose override의 역할이 바뀌었다

`docker-compose.override.yml`이 backend를 `8083:8081`로 돌리고 있었다 — 낡은 `:8081`
프로세스를 피하려고 그날 만든 임시 파일이었고, 주석이 *"그 프로세스를 정리한 뒤에는 이 파일을
지우면 원래로 돌아간다"*고 적어뒀다. 그 프로세스가 사라졌으므로 지울 때였다.

**그냥 지우면 다른 충돌이 생겼다** — compose의 `ai-engine`이 호스트 `:8000`을 잡는데 MaintQ
백엔드가 거기 있었다. `insuq-af`가 **override의 역할을 바꿔** 해결했다(backend 8083 매핑 제거
→ ai-engine 호스트 포트 제거). Spring은 컨테이너 네트워크로 `ai-engine:8000`을 부르므로
호스트 노출이 필요 없다.

⚠️ **compose의 `ports`는 override에서 덮어쓰기가 아니라 병합이다** — 그냥 적으면 원본과
합쳐져 둘 다 뜨려다 실패한다. `ports: !override` 태그가 필요하다(`maintq-45` 실측).

## 3. 🔴 촬영이 드러낸 실동작 결함 3건

**셋 다 API 검증만으로는 보이지 않는다.** 이게 이 세션의 핵심 산출물이다.

### ① `.env`가 코드 수정을 무력화하고 있었다

```
MAINTQ_A2A_INSUQ_BASE_URL=http://localhost:9102
```

2026-08-30에 `backend/routers/a2a.py`의 **기본값**을 `:8081`로 고쳤는데, `.env`에 환경변수가
명시돼 있어 그게 이겼다. **즉 그 한 줄 수정이 한 번도 효과를 낸 적이 없었다.**

당시 나는 "환경변수 오버라이드가 있어 코드 수정 전에도 동작한다"고 했는데, **실제로는 그
오버라이드가 반대 방향으로 걸려 있었다.**

### ② MCP 도구가 자기 자신에게 못 닿았다

```
search_insurance_clause → [WinError 10061] 연결이 거부됨
화면: "InsuQ 로부터 확답을 받지 못했습니다"
```

InsuQ 문제로 보였지만 아니었다. `mcp_server/tools/search_insurance_clause.py`의
`_DEFAULT_BASE_URL = "http://localhost:8000"` — **MCP 도구는 MaintQ 자기 백엔드를 부른다.**
백엔드를 `:8897`로 옮기면서 그 주소를 비웠다.

```
화면 → 채팅 → MCP 도구 → MaintQ backend(:8000 ← 비었음!) → /api/a2a/lookup-clause → InsuQ
                            ↑ 여기서 끊김
```

**`maintq-45`가 앞서 받은 200은 `curl`로 `:8897/api/a2a/lookup-clause`를 직접 찍은 것**
— MCP 도구를 건너뛴 다른 경로였다. 그래서 두 결과가 갈렸다.

### ③ FinAllQ 토큰이 낡아 2차 홉만 막혔다

```
FinAllQ infra/.env  INSUQ_SERVICE_TOKEN : 32자
InsuQ   backend/.env A2A_MOCK_TOKEN     : 44자   → 불일치
```

- 1차 홉(MaintQ→FinAllQ) **200**
- 2차 홉(FinAllQ→InsuQ `verify-collateral-insurance`) **401**
- FinAllQ가 그걸 **502로 감싸** 내보냄 → 화면엔 "FinAllQ A2A 어댑터에 연결할 수 없습니다"

**502라 FinAllQ 자체 장애로 오진하기 쉽다.** 실제로는 FinAllQ가 멀쩡하고 InsuQ 인증이 막힌
것이다.

**진단법 — 스킬별 성공/실패 패턴으로 홉을 좁힌다.** 어댑터 로그에서
`request-withdrawal`·`request-settlement`는 200인데 **`assess-loan`만 502**였다.
같은 어댑터인데 **2차 홉이 있는 스킬만 실패**하면 원인은 어댑터가 아니라 그 홉에 있다.

✅ 2026-09-01 FinAllQ가 토큰을 동기화해 해소. ⚠️ **단 실호출 검증은 아직이다** — 스택을
내린 뒤 고쳐서 InsuQ 왕복을 못 태웠다. **고쳤다는 것과 통한다는 것은 다르다.**

## 4. 「성공은 로그를 안 남긴다」 — 하마터면 산출물을 의심할 뻔했다

`insuq-af`가 보고했다: *"기동 후 29분간 InsuQ에 도달한 A2A 호출이 0건"*.

그런데 내 시나리오 ①은 성공했고 InsuQ 형식 그대로의 응답(판정 판단 유보, 근거 8건, 페이지
번호)을 9.4초에 받았다. **둘 중 하나였다** — 로그 조회가 틀렸거나, **MaintQ가 캐시에서
응답했거나.** 후자라면 **GIF가 "실시간 A2A 호출"처럼 보이는데 실제로는 캐시**라는 뜻이고,
그건 산출물의 정직성 문제라 그냥 넘길 수 없었다.

**확인 결과 캐시가 아니었다.** ai-engine이 `POST /qa`를 4건 받았고 `10:21:11`이 촬영
시간대와 맞물린다(내가 직접 로그로 재확인).

**착오의 원인:** `ServiceTokenFilter`는 **실패만 WARN을 남기고 성공은 조용하다.**
`insuq-af`가 "10:08 이후 실패 로그 없음"에서 "호출 없음"을 도출했는데, **성공한 호출은 원래
안 보인다.** 내가 직접 본 backend 로그도 똑같이 두 건뿐이었으니 나 혼자 봤어도 같은 결론에
빠졌을 것이다.

⇒ **이 스택에서 A2A 성공을 확인하려면 ai-engine의 `POST /qa`를 본다:**
```bash
docker compose logs -t ai-engine | grep "POST /qa"   # tail 금지 — 헬스체크에 묻힌다
```

## 6. 내가 지킨 경계

- **FinAllQ 로그인은 사용자가 눌렀다.** 데모 계정이 화면에 이미 채워져 있었지만 자격증명으로
  인증하는 동작이라 내가 하지 않았다.
- **결재함의 승인·반려를 누르지 않았다.** 촬영 목적은 "도착했다"를 보여주는 것이고, 누르면
  되돌릴 수 없는 금융 승인이다(그리고 `finallq-91` 지적대로 FDS 판정이 끼어들어 화면도
  복잡해졌을 것이다).
- **`insuq-af`가 권한 거부된 작업(`Stop-Process`)을 대신 하지 않았다.** 사용자에게 올렸고,
  사용자가 `maintq-45`에 맡기기로 결정했다. 그마저도 결국 사용자가 직접 java를 종료했다.
- **`FinAllQ/infra/.env`를 고치지 않았다.** 런타임 환경변수로 어댑터만 재기동해 촬영을 마치고,
  파일 수정은 `finallq-91`에 넘겼다(그쪽도 사용자 승인을 받고 진행했다).

- **compose `ports`는 override에서 병합된다** — `!override` 태그 필요
- **API 검증 ≠ 화면 동작.** 이 세션에서 세 번 반복됐다. 구성 변경 후에는 **화면 경로(채팅)로**
  검증한다
- MaintQ 프론트는 `:8897`(도커 판)을 본다 — 백엔드를 맨 프로세스로 띄우면 포트를 맞춰야 한다

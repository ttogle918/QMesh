## 1. 계약 문서 확정 (오전~오후 초반)

### 배경
`A2A_CONTRACT_CHANGES.md`에 CP-001(InsuQ 스킬 5종 — 거부 표현·근거 인용 표준화)이
"제안" 상태로 걸려 있었고, `A2A_IDENTITY.md`의 "미결 사항" 5개 중 실제로는 3개가 이미
본문에 결론이 나 있었는데 "미결" 제목 아래 묻혀 있었다. 문서 구조(스키마·Agent Card·
README 목록 정합성)도 재점검이 필요했다.

### 한 일과 이유
- **CP-001 → 채택 전환**: 세 레포(FinAllQ·InsuQ·MaintQ) 전수 확인 결과 이 스킬들을
  참조하는 코드가 0건이라, 지금이 계약을 고쳐도 위험이 가장 적은 시점이었다. 스키마
  5개 파일에서 `PROPOSED(...)` 마커만 제거하고(내용은 이미 반영돼 있었음), 상태 표를
  `채택`으로 바꿨다. **단, MaintQ·FinAllQ 쪽 확인 체크리스트는 체크하지 않았다** — 그건
  각 레포가 실제 구현하며 스스로 확인할 일이지 문서 확정으로 대신할 수 없어서.
- **A2A_IDENTITY.md 미결 사항 재정리**: 5개 항목 중 3개(대리 여부·자격증명 발급 주체·
  대출심사 성격)는 이미 결론이 있어 `✅ 해결됨`으로 승격했고, 나머지 2개(출금 파이프라인
  여부·감사로그 외부 actor)는 원문에 이미 "FinAllQ 구현 시 결정"이라 적혀 있어 QMesh가
  지금 대신 정할 수 없는 항목이라 `⏸ FinAllQ 구현 착수 시 결정 (QMesh 비차단)`으로
  라벨만 명확히 했다. **결론을 새로 만든 게 아니라 이미 있던 결론과 진짜 미결을
  구분해서 드러낸 것**.
- **문서 구조 점검**: 스키마 12종 = Agent Card 스킬 id 12종 = README 목록 12종 —
  전수 대조 결과 drift 없음. `ref_insuq`·`ref_maintq`·`ref_finallq` 세 인덱스 문서도
  "원본은 A2A_Q, 복제 안 함" 원칙을 일관되게 지키고 있어 별도 수정 없이 마무리.

### 이 과정에서 발견한 것
최종 브랜치 리뷰(subagent-driven-development 흐름의 마지막 단계)에서 **CP-001 섹션
제목이 여전히 `(제안)`인데 바로 아래 상태 표는 `(채택)`이라 모순**된 걸 잡아냈다 —
이 문서 자체가 "`제안`/`채택` 단어가 합의 여부를 나타내는 유일한 신호"라고 스스로
못박아뒀기 때문에 사소한 게 아니었다. 그 자리에서 고치고 마무리.

## 2. InsuQ `lookup-clause` A2A 어댑터 (오후)

### 왜 이 스킬을 첫 조각으로 골랐나
시나리오 문서(`docs/A2A_SCENARIOS.md`)가 이미 "정책 원장 등 선행조건이 없어 A2A를 가장
싸게 증명할 수 있는 스킬"로 지목한 것이었고, InsuQ 코어(약관 검색·인용·거부)는 이미
동작 중이었다(`InsuQ/ai-engine`의 `POST /qa`, 실측 확인).

### 설계 결정과 이유
- **어댑터를 InsuQ 코드 안이 아니라 A2A_Q 안에 독립 FastAPI 서비스로 프로토타입**한다 —
  InsuQ 자체 문서(`A2A_API_SPEC.md`)는 "A2A 수신부는 Spring(backend)에 둔다"고 이미
  결정해뒀지만, `lookup-clause`는 DB가 필요 없는 순수 RAG 스킬이라 그 제약이 꼭
  필요하지도 않고, A2A_Q 안에서 먼저 프로토타입하면 InsuQ 코드를 전혀 안 건드리고
  빠르게 증명할 수 있어서.
- **포트 `:9102`** — README의 InsuQ 정식 포트 `:9002`와 구분(나중에 InsuQ가 Spring에
  실제 구현할 자리와 헷갈리지 않게).
- **`lookup-clause` 계약 자체가 없어서 신규 작성** — 기존 5종 스킬을 바꾸는 게 아니라
  순수 추가라, CP 합의 절차 없이 바로 스키마·Agent Card에 추가했다.

### 구현 (6개 태스크, TDD)
계약+스캐폴딩 → pydantic 모델 → InsuQ 응답 매핑 로직 → InsuQ HTTP 클라이언트 →
Agent Card 로더 → FastAPI 배선. 태스크마다 구현 서브에이전트 → 리뷰 서브에이전트
승인까지 거쳤다.

### 리뷰에서 나온 것과 처리
- Task 3 리뷰: `clause_no`(문자열) 생략 판정을 `is not None`으로 통일했다가, 빈
  문자열(`""`)이 있으면 오히려 깨지는 회귀를 발견 — `page`(정수, 0이 유효값일 수 있음)와
  `clause_no`(문자열, 빈 문자열도 "없음")는 성격이 달라서 원래대로 진리값 체크로
  되돌렸다. **"일관성"이라는 이유로 서로 다른 타입의 필드를 같은 방식으로 처리하면
  안 된다**는 교훈.
- 전체 브랜치 최종 리뷰(opus)에서 7건 발견 → 한 번에 수정: `confirm_required`가
  `completed` 분기에서 누락되던 것, 업스트림 예외 처리가 `ConnectError`·`TimeoutException`
  두 개만 잡던 것을 `TransportError`(형제 예외들 전부 포함)·`HTTPStatusError`·
  비-JSON 응답까지 넓힘, `KNOWN_SKILL_IDS`를 하드코딩 목록 대신 Agent Card에서
  동적으로 뽑도록(스킬이 추가돼도 안 깨지게), 응답을 pydantic으로 실제 검증하도록,
  잘못된/비객체 JSON 본문이 500으로 새던 것 방지.

### 최종 상태
25개 테스트 전부 통과, 실제 `uvicorn`으로 `:9102` 기동해 Agent Card 응답까지 확인.

## 3. FinAllQ `request-withdrawal` A2A 어댑터 (저녁)

### 왜 이 스킬을 두 번째로 골랐나
시나리오 문서가 "레일은 다 깔렸고 문(창구)만 없다"(75% 준비도)로 지목한 스킬이고,
FinAllQ 자체 트러블슈팅 문서(`docs/troubleshooting/2026-08-20_a2a-contracts-drift.md`)로
이체·결재 흐름(`TransferController`, Sprint 7~14)이 실제로 동작 중임을 확인했다.

### InsuQ와 다른 두 가지 벽
1. **인증**: FinAllQ의 실제 이체 API(`POST /api/v1/transfers`)는 로그인된 사용자를
   요구한다(`@AuthenticationPrincipal`). 파트너 자격증명(머신 신원, 백로그 131·132)이
   아직 없어서 — **시드 데이터의 서비스 계정(`demo-employee@finallq.example`)으로
   로그인해 JWT를 받는 임시 방식**을 택했다. 실제 머신 신원이 생기면 `auth.py` 한
   파일만 바뀌도록 분리해뒀다.
2. **계약 갭**: 기존 `request-withdrawal.json` 스키마엔 계좌번호 필드가 아예 없었다 —
   `supplier`(거래처명, 자유 텍스트)만으로는 실제 이체를 호출할 방법이 없어서
   **CP-002**(`to_account_number` 필수·`to_bank_code` 선택 추가)를 새로 제안하고
   `제안` 상태로 기록했다(MaintQ가 발주서에 거래처 계좌번호를 갖고 있는지 확인 필요).
   `from_account_id`는 스키마에 넣지 않았다 — "어느 계좌에서 나가는지"는 호출자(actor,
   서비스 계정)에 딸린 정보이지 MaintQ가 지정할 subject가 아니라는 원칙
   (`A2A_IDENTITY.md` 결정 1) 때문에, 어댑터가 로그인한 계정의 계좌를 자동 조회하게
   설계했다.

### 구현 (7개 태스크, TDD)
CP-002+스캐폴딩 → pydantic 모델 → 응답 매핑(FinAllQ `TransferStatus` 6종 → A2A
`status` 3종) → 서비스 계정 로그인+토큰 캐시 → FinAllQ HTTP 클라이언트 → Agent Card
로더 → FastAPI 배선(+ 401 받으면 캐시 버리고 1회만 재로그인 후 재시도, 무한 재시도
금지).

### 전체 브랜치 최종 리뷰(opus)에서 나온 6건과 처리
- **`memo` 100자 자르기 누락** — 계획 문서 자체가 "자른다"고 적어놓고 코드에서 빠뜨린
  것. FinAllQ가 100자 제약(`MEMO_MAX_LENGTH`)을 갖고 있는데 이걸 안 지키면, 101자
  이상인 유효한 A2A 요청이 FinAllQ 쪽 검증 실패로 튕기고 어댑터는 그걸 "스키마 위반"
  이라고 잘못 보고하는 상황이 생긴다. 한 줄 수정.
- **`request_chain_id`가 InsuQ·FinAllQ 두 어댑터 모두의 404/501 응답에서 빠져 있던
  것** — 개별 태스크 리뷰에선 "사소한 지적"처럼 보였지만, 전체 브랜치 리뷰에서 보니
  **두 어댑터가 똑같이 틀려서 이게 "정착된 패턴"이 되기 직전**이었다. 둘 다 한 번에
  고쳤다 — MaintQ 어댑터가 세 번째로 생기기 전에.
- **계좌번호 정규식(CP-002가 추가한 `pattern`)이 pydantic에서 실제로는 검증 안 되고
  있던 것**, **FinAllQ 403(권한 없음)이 502(장애로 보임)로 뭉개지던 것** — 둘 다
  "일단 되니까 넘어갈 뻔한" 것들인데, 각각 잘못된 계좌번호·서비스 계정 권한 문제를
  디버깅할 때 완전히 엉뚱한 방향(FinAllQ가 죽었나?)으로 유도할 수 있어서 고쳤다.
- **토큰 캐시에 락이 없는 것** — 이건 의도적으로 안 고쳤다. 동시 요청 간 경쟁
  조건이 있지만 정확성은 안 깨진다(발급된 토큰은 뭐가 됐든 유효). 프로토타입 규모에서
  `asyncio.Lock`을 넣는 복잡도가 이득보다 크다고 판단 — **코드가 아니라 주석으로만
  이 판단을 남겼다**.

### 최종 상태
91개 테스트 전부 통과(InsuQ 31 + FinAllQ 60 근처), 실제 기동 확인 완료.
`feat/finallq-a2a-adapter` 브랜치를 `main`에 fast-forward 머지, 브랜치 삭제.

## 4. MaintQ A2A 아웃바운드 클라이언트 — 설계만 (밤)

### 이번엔 코드를 안 짠 이유
사용자가 "코드는 다른 데서 작성할게"라고 명시적으로 요청 — 이 라운드는 브레인스토밍→
스펙 작성까지만 하고, writing-plans·subagent-driven-development는 진행하지 않았다.

### MaintQ 쪽이 이미 준비해둔 것 (실측)
- `backend/a2a/credentials.py` — 파트너(`finallq`/`insuq`)별 `client_id`/`client_secret`을
  환경변수에서 읽는 계층. 자체 docstring이 "토큰 캐시는 호출부가 생기는 스프린트가
  만든다"고 이미 자리를 비워뒀다.
- `partner_links` 테이블(D91~D96) — subject 매핑 대장. 시드에
  `finallq|company|''|LINKED|CMP-MAINTQ-001` 행이 이미 있음.
- `traces.request_chain_id` 컬럼 — 있지만 "쓰는 쪽 없음"으로 명시된 상태.
- 실제 트리거 함수까지 확인: `backend/services/po.py::transition(po_id, "approved", ...)`
  가 S5(출금 요청)의 실제 발화점.

### 핵심 설계 판단 — 인증 모델 간극을 어떻게 다뤘나
`credentials.py`는 OAuth2 client-credentials(토큰 교환)를 상정하는데, 오늘 만든 두
어댑터는 그 흐름을 검증하지 않는다(InsuQ는 인증 자체가 없고, FinAllQ는 사람 계정
로그인). **지금은 `credentials.load()`로 얻은 값을 헤더에 실어 보내고, 어댑터가 검사
안 해도 무시되게 둔다**는 쪽으로 결정 — 나중에 실제 토큰 교환이 붙어도 호출부 코드는
안 바뀌게, 헤더 생성 로직만 별도 함수(`build_auth_header`)로 격리했다.

### 설계 중 새로 발견한 것
**MaintQ의 `suppliers` 테이블에도 계좌번호 컬럼이 없다** — CP-002(FinAllQ 쪽에서 발견한
것과 완전히 같은 종류의 갭이 MaintQ 쪽에도 있다는 뜻. `to_account_number`를 실제로
채우려면 MaintQ가 먼저 `suppliers.account_number` 컬럼을 추가해야 한다. 이 문서는
이걸 **기록만** 하고, 실제 마이그레이션 결정은 MaintQ 레포 쪽에 남겼다.

### lookup-clause는 트리거 성격이 다르다는 것도 설계에 반영
`request-withdrawal`은 상태 전이(발주 승인)가 트리거지만, `lookup-clause`는 그런
이벤트가 없다 — 사람이 화면에서 직접 묻는 **질의형** 트리거다. 승인 게이트는 필요
없다고 판단했다(돈·계약이 안 움직이는 순수 조회라 QMesh 관통 원칙에 안 걸림). 단
MCP 도구에서 직접 호출하지는 않는다 — "LLM이 A2A 호출 여부를 결정하지 않는다"는
기존 원칙(D15, 신원 위조 방지와 같은 이유)을 조회형 스킬에도 그대로 적용했다.

### 산출물
`docs/superpowers/specs/2026-08-21-maintq-a2a-outbound-client-design.md` — 일반
아키텍처(5단계 파이프라인) + `request-withdrawal`·`lookup-clause` 두 스킬의 구체적
설계(트리거·payload 조립 코드·응답 처리·trace 기록) + 나머지 8개 트리거는 표로만.

- **파트너 자격증명(머신 신원, FinAllQ 백로그 131·132)** — FinAllQ 어댑터의 서비스

- **`suppliers.account_number` 마이그레이션** — MaintQ 쪽에서 결정할 일로 기록만 남김
- **멱등성(`Idempotency-Key`)** — 두 어댑터 모두 스코프 밖으로 명시. 504 타임아웃 후
  재시도 시 중복 요청이 생길 수 있다는 위험을 설계 문서에 남겨둠

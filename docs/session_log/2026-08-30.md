## 1. 어제 작업의 결말 — A안

InsuQ가 `gpt-oss-120b`를 실기동 게이트에서 기각했고, 최종 구성은 이렇게 닫혔다.

| | 기본 | 폴백 |
|---|---|---|
| MaintQ | `nvidia` / `openai/gpt-oss-120b` (무료) | `openai` / `gpt-4.1-mini` |
| InsuQ | `openai` / `gpt-4.1-mini` | **없음(의도적)** |

**"맞추자"는 원래 목표를 증거에 맞춰 포기했다.** 두 파이프라인이 같은 모델을 요구하지
않는다 — InsuQ에는 `tools`를 끄고 답변을 강제하는 턴(`tool_loop.py::_final_turn`, D14a)과
8초 라우터·30초 예산이 있고 MaintQ에는 없다. **파이프라인 구조가 모델 적합성을 가른다.**

InsuQ 폴백을 비운 것도 의도적이다 — 유일한 대안이 게이트를 통과 못 하므로 켜두면
장애 시 더 나쁜 모델로 떨어진다.

**어제 기록한 내 판단 오류 2건은 그대로 유효하다**(2026-08-29 §7 참고): 합성 재현
44회가 정상이라는 이유로 실제 게이트의 2회 재현을 의심한 것, 그리고 제안한 지렛대
두 개(`thinking=false`·`reasoning_effort=low`)가 둘 다 역효과였던 것.

## 3. TASK-H09 — 사용자 기억이 틀렸음을 코드로 확인

사용자 질문: *"lookup-clause를 spring으로 옮길 수 있어? fastapi여만 해서 그 위에 fastapi
서버를 씌웠던 거 같은데"*

**옮길 수 있었다.** 헷갈린 지점은 이해할 만하다 — RAG 엔진(`ai-engine`, :8000)이 FastAPI인
건 맞다. 하지만:

1. **Spring이 이미 같은 엔드포인트를 부르고 있었다** — `AiEngineClient.java:53`의
   `qa(AiQaRequest)`가 `POST /qa`를 호출한다. FastAPI 어댑터가 부르는 것과 정확히 같다
2. **어댑터 자기 docstring이 존재 이유를 적어놨다** — *"InsuQ **코드를 건드리지 않고**
   기존 `POST /qa`를 A2A 봉투로 감싼다"*. 기술적 필요가 아니라 프로토타이핑 편의였다
3. **전례가 있었다** — 같은 docstring에 `verify-collateral-insurance`·`claim-insurance`가
   한때 FastAPI에 있었으나 Spring 구현과 **계약이 갈라지는 중복** 때문에 제거했다고
   적혀 있었다. `lookup-clause`가 마지막 하나였다

### 위임하며 건 순서 제약이 값을 했다

"**Spring 경로가 실측으로 동작하는 걸 확인하기 전에는 `a2a_adapter/`를 지우지 말라**"고
명시했는데, 실제로 백로그가 *"`a2a_adapter`는 compose·CI 어디에도 안 묶여 있다"*고
적고 있었으나 **`docker-compose.yml`에 서비스 정의가 실제로 있었다.** 확인 없이 지웠으면
compose가 깨졌다.

### 🔴 실기동에서만 드러난 인가 공백

`lookup-clause`가 **어느 `allowed_skills`에도 없었다.** 포크 어댑터에 인증·인가 계층이
**아예 없어서**(그 compose 주석이 스스로 "Bearer·X-A2A-Partner-Id 미검증, 외부 공개 금지"
라고 적고 있었다) grant 없이 돌던 것이다. Spring으로 오면서 `ServiceTokenFilter`가
403으로 막게 되어 grant 마이그레이션이 신설됐다 — **권한 확대가 아니라 이관 전 접근을
유지하는 변경이다.**

**단위·통합 테스트로는 절대 안 드러나는 종류다** — 테스트가 시드 grant를 자체로 넣는다.

결과: HTTP 200(12.1초), 인용 9건 전부 계약 정규식 통과, 미인가 403 · 잘못된 토큰 401.
Agent Card가 한 곳에서만 서빙된다.

## 4. S12·S13 — 5종 중 2종만 만들기로 한 판단

브레인스토밍 첫 단계에서 **5종이 동등하지 않다**는 게 나왔다. 각 스킬의 필수 입력을
MaintQ가 실제로 채울 수 있는지 `data/seed.py` 스키마로 대조했다.

| 스킬 | MaintQ 데이터 | 판정 |
|---|---|---|
| S13 `assess-used-equipment-loan` | `assets.building_id`·`acquired_at`·점검일 3종 + `ownership_checks` | ✅ 만든다 |
| S12 `request-settlement` | `assets.has_lien`·`lien_creditor`·`lien_consent_ref`·`decisions` | ✅ 만든다 |
| S6 `advise-hedge` | 🔴 통화·외화 데이터 **0건** | ❌ |
| S16 `advise-financing` | 트리거가 될 도메인 이벤트가 없다 | ❌ |
| S15 `advise-replacement-financing` | 🔴 `claim-insurance` 발신 흐름 자체가 없다 | ❌ |

**3종은 "미착수"가 아니라 "데이터 없음"으로 닫았다.** S6를 만들려면 공급사에 통화
컬럼을 신설하고 환노출을 지어내야 하는데, 이 프로젝트는 그러지 않는 것을 원칙으로
삼아 왔다(D62·D74·D76). **스킬 개수를 늘리려고 그 원칙을 깨지 않는다.**

### LIEN-CONSENT 교착 — 교착이 아니었다

S12 계약이 `decision_id`(처분 결정)를 필수로 요구하는데 LIEN-CONSENT는 `BLOCKING` 룰이라
처분 결정을 막는다. 순서 교착으로 보였다:

> 결정이 있어야 정산 요청 → 정산돼야 담보 풀림 → 담보 풀려야 결정 가능

사용자가 "먼저 코드로 확인해 달라"를 택했고, 확인 결과 **교착이 아니었다**:

1. **LIEN-CONSENT는 서명을 막지 draft 생성을 막지 않는다** —
   `ALLOWED_FROM = {"pending": "draft", "signed": "pending", ...}`, 차단 판정은 서명
   단계에서만 걸린다(`decisions.py`: `verdict in BLOCKING_VERDICTS and override is not
   True → OverrideRequired`)
2. **담보 자산도 evidence_bundle이 만들어진다** — `build_evidence_bundle.py`가 계약
   조항을 `law_text_unavailable` 검사에서 **의도적으로 제외**했고 그 이유를 *"검사에
   넣으면 LIEN-CONSENT가 걸린 자산의 번들이 구조적으로 영원히 불가능해진다"*로 적어뒀다
3. **draft 생성 경로가 실재한다** — `generate_disposal_document.py:329`

**따라서 계약을 고칠 필요가 없었다.** `decision_id`가 draft를 가리키면 된다.

### 해소는 `flags`가 아니라 `assets.lien_consent_ref`다

`data/rules/rules/LIEN-CONSENT.json`을 읽고 확정했다:

```json
"trigger": {"all_of": [{"field": "has_lien", "op": "eq", "value": true},
                       {"field": "lien_consent_ref", "op": "is_null"}]},
"resolve_options": ["금융기관 동의서 확보 후 첨부 (lien_consent_ref 등록)",
                    "대출 상환 후 근저당 말소"]
```

룰이 읽는 필드는 `lien_consent_ref` 하나다. `flags` 테이블은 해소 라이프사이클이
설계돼 있으나 **쓰기 경로가 없어 0행**이고 룰 평가에 관여하지 않는다 — 거기 쓰는 것은
해소가 아니다. **S12는 정확히 `resolve_options[1]`의 자동화다.**

## 5. 계약 갱신 — "왜 통과하는가"가 중요했다

FinAllQ 세션에 물었다: *"수신부가 `decision_id`의 서명 여부를 검사합니까?"*

답: **받아들인다. 단 "허용하기로 결정해서가 아니라 검사할 수단이 없어서"다.**
저장소 전체에서 `decision_id` 사용처가 `a2a_adapter/schemas.py:235`의 pydantic 필드 선언
**한 줄뿐**이고 `decide_settlement()`에 인자로 전달조차 되지 않는다.

**그 구분이 이 답변에서 제일 중요한 부분이었다.** 없었으면 "지금 통과하니 괜찮다"로
넘어갔을 테고, 나중에 누군가 "`decision_id`는 서명된 결정을 가리킨다"고 가정하고
검증을 추가하면 조용히 깨졌을 것이다.

→ `docs/schemas/request-settlement.json`에 명시했다(`9d7cf91`). **구조는 안 바꾸고
`description`만 추가**했으므로 FinAllQ pydantic 모델은 영향받지 않는다.

`approved_by`도 함께 명시했다 — **정산 요청 승인자**이지 처분 서명자가 아니다.
draft 결정은 `reviewed_by`가 NULL이라 거기서 읽으면 항상 빈다(내가 스펙 자체 검토에서
잡은 모순이다).

### 범위 밖으로 둔 것

FinAllQ Pool 200의 `loan_id` 부재 갭(여신 잔액 미반영, 음수 `remaining_balance` 경계).
**S12는 판정만 하고 장부를 갱신하지 않는다** — `decide_settlement()`가 DB 조회 0인 순수
함수다(TASK-195의 명시적 설계 판정). `assess-loan`이 판정만 하고 대출을 실행하지 않는
것과 같은 성격이라 결함은 아니지만, 모르고 쓰면 "정산이 끝났다"고 오해하므로 설계
문서에 적어 뒀다.

## 6. 내 계획서 오류 5건 (MaintQ 세션이 잡음)

| 항목 | 실제 |
|---|---|
| `con.commit()` | **중복이 맞았다** — `connect()`가 컨텍스트 종료 시 커밋한다. 내가 「알려진 위험」에 적어둔 게 적중 |
| 픽스처 `tmp_db`·`fetch_asset`·`fetch_decision` | **이 레포에 없다.** 관례는 `db_path` + 테스트가 직접 심기(`seed_po` 선례) |
| `error_codes` 65 | **70이 맞다** — D109(Sprint 15)가 IE5 5건을 병합했다. 낡은 숫자를 옮겨 적었다 |
| 자산 ID | S12·S13 픽스처가 `AST-L3-CONV`로 충돌 → `AST-LIEN`/`AST-NOLIEN`으로 분리 |
| `_dispatch`가 기존 엔드포인트 미변경 | ⭕ 지켜졌다 |

**계획서에 "기존 관례를 먼저 읽으라"고 여러 곳에 적어둔 것이 이 오류들을 흡수했다** —
그래서 레포 세션에 위임한 것이기도 하다.

**계획에 없던 검사도 하나 추가됐다** — `lien_released` 키가 **아예 없을 때** 아무것도
안 쓰는지. 내 계획은 `false`만 테스트하고 키 부재를 빠뜨렸다. `is True` 검사를 쓴
이유(truthy면 `"true"` 문자열이나 `1`도 담보를 푼다)도 주석으로 남았다.

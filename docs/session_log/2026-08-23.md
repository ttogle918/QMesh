## 1. FinAllQ `request-withdrawal` — 배포 백엔드 실제 E2E (오전)

### 왜 이걸 먼저 했나
어제 만든 어댑터는 유닛 테스트(모킹) 91건만 통과한 상태였다 — 실제 배포 백엔드에
네트워크로 붙어본 적은 없었다. "서비스 계정 로그인부터 확인. 안 되면 자격증명부터
같이 찾자"가 오늘의 첫 지시였다.

### 한 일과 이유
- 자격증명 위치부터 찾았다 — FinAllQ 레포의 `infra/deploy/deploy.env`(gitignore)와
  `docs/dev-accounts.md`(gitignore) 둘 다 `demo-employee@finallq.example` /
  `Test1234!`를 가리키고 있었다. **새로 만들 필요 없이 이미 로컬에 있었다.**
- 배포 백엔드(`https://backend-core-dz5zeqmb3a-du.a.run.app`)에 직접 curl로 로그인 →
  200 확인. 계좌 조회(`GET /api/v1/accounts`) → 실계좌(`accountId: 1`, 잔액 3억) 확인.
- 어댑터를 로컬에서 그 배포 백엔드를 가리키도록(`FINALLQ_BASE_URL` 환경변수) 띄우고
  `POST /a2a/skills/request-withdrawal`을 실제로 호출.

### 발견한 것 — bash 쉘 이스케이핑
curl `-d`에 한글이 섞인 JSON을 인라인으로 넣으면(Windows Git Bash) 본문이 깨져
어댑터가 "request body must be a JSON object"로 잘못 튕겼다. 어댑터 버그가 아니라
쉘 문제였다 — 이후 전 구간에서 페이로드를 파일로 써서 `--data-binary @file`로
보내는 방식으로 바꿨다(오늘 나머지 curl 테스트 전부 이 방식).

### 최종 상태
전체 경로(로그인 → 계좌 조회 → 이체 요청)가 실제로 통과했다:
`{"status":"input-required","req_id":"3"}` — FinAllQ 쪽에 실제 `PENDING` 이체
요청이 하나 생겼다(재무 승인 대기, 예상대로).

## 2. InsuQ `lookup-clause` — 로컬 ai-engine 실제 E2E (오전~낮)

### 왜 로컬로 했나
InsuQ는 배포본이 없다 — ai-engine을 로컬로 띄우는 수밖에 없었다. `ai-engine/.venv`가
이미 있어 `uvicorn insuq_ai.api.main:app --port 8000`으로 시도했는데, **포트 8000이
이미 다른(무관한) 프로세스에 점유돼 있었다** — uvicorn 자체는 모델 로딩까지 전부
성공(`Application startup complete`)했지만 바인드에서 실패. 포트를 8001로 바꿔 재시도해
정상 기동.

### 한 일과 이유
- 어댑터(`:9102`)를 이 로컬 ai-engine(`:8001`)을 가리키도록 띄우고 두 종류의 질문을
  실제로 보냈다:
  1. **도메인 밖 질문**(화재보험) → "약관에서 확인 불가" 정상 거부. 근거 없으면 거부
     원칙이 실제로 동작함을 확인.
  2. **도메인 안 질문**(실손의료) → **첫 호출이 504 timeout으로 실패**했다.

### 발견한 것 — 콜드 스타트 타임아웃 갭 (수정은 보류)
어댑터의 InsuQ 호출 타임아웃이 10초 하드코딩(`adapters/insuq_a2a/insuq_client.py`)인데,
이 서빙 arm(HyDE 질의 확장)은 질의당 LLM 호출이 1회 추가돼 콜드 상태에서 10초를 넘길
수 있다. 실측: ai-engine 직접 호출로 첫 실손 질문이 실제로 10초를 넘겼고, 캐시가 워밍된
뒤 재요청은 1초 미만이었다(재요청 시 실제 근거 조항 인용을 포함한 정상 답변 수신).
설계 문서가 명시한 p95 7.07초는 웜 상태 기준으로 보인다.

**사용자 결정: 지금 고치지 않는다.** 기록만 남기고 3단계(MaintQ 테스트)로 넘어감 —
프로토타입 규모에서 10초 → 20~30초로 늘리는 건 한 줄 수정이지만, 오늘 순서를 지키는
게 더 중요하다고 판단.

### 최종 상태
E2E 경로 자체는 확인됨(거부 경로 + 정상 답변 경로 둘 다 실측). 콜드 타임아웃은
알려진 이슈로 남겨둠 — `adapters/insuq_a2a/insuq_client.py`의 `timeout: float = 10.0`
기본값이 위치.

## 3. MaintQ A2A 코드 테스트 75건 (낮)

### 배경
MaintQ 쪽엔 어제 세션 이후 사용자가 별도로 A2A 아웃바운드 클라이언트 실제 구현을
끝내둔 상태였다(`backend/a2a/credentials.py`·`auth_header.py`·`client.py`·`trace.py`·
`payloads.py`, `routers/a2a.py`, `routers/po.py`의 S5 디스패치 트리거). **테스트는
0개**였다 — 오늘 지시사항 3번.

### 설계 결정 — 왜 `backend/conftest.py`를 새로 만들었나
기존 유일한 테스트(`backend/agent/test_llm_cache.py`)는 DB를 안 쓰는 순수 로직
테스트였다. A2A 코드는 SQLite(`traces`·`partner_links`·`po_drafts`·`suppliers` 등)를
직접 건드리므로 새 픽스처가 필요했다. `data/seed.py`의 프로덕션 DDL 전체(20여 테이블)를
끌어오는 대신, A2A 경로가 실제로 쓰는 컬럼만 발췌한 최소 스키마를 만들었다 — 유지비
트레이드오프를 문서 주석에 명시.

### 구현 (8개 테스트 파일, 실제 네트워크 0건)
- `credentials.py`·`auth_header.py`: 순수 로직(env 파싱, Basic 헤더 조립) — DB·네트워크
  불필요
- `trace.py`·`payloads.py`: `conftest.py`의 SQLite 픽스처로 실제 DB round-trip
- `client.py`: `httpx.AsyncClient`를 자체 제작한 `_ScriptedAsyncClient`로 대체해
  타임아웃·연결실패·5xx·403 등 전 경로 검증
- `routers/a2a.py`: `call_skill`을 monkeypatch한 FastAPI `TestClient`
- `routers/po.py`(S5 트리거): **팀장이 아니면 A2A 호출까지 도달 못 하는지**,
  **A2A 전송 실패가 승인 자체를 되돌리지 않는지** 두 계약을 특히 집중 검증

### 발견한 것 — 실행 환경
MaintQ 자체 `.venv`엔 pytest가 없다(전역 설치된 시스템 Python으로 돈다는 걸 실측으로
확인 — 기존 테스트 실행 관례를 그대로 따름). 전체 스위트 실행 중 Windows
`WinError 10014`(socketpair) 플레이키가 간헐적으로 나타났는데, 격리 실행하면
사라지는 걸 확인해 회귀 아님으로 판단.

### 최종 상태
75/75 신규 테스트 통과(기존 24개 포함 총 99개, 그중 2개는 이 세션과 무관한 사전
실패 — 전역 환경에 `google-genai` 패키지 부재). 커밋은 이 시점엔 보류(MaintQ에
다른 미커밋 작업이 많아서) — §5에서 재정리.

## 4. S8 멀티홉 — 브레인스토밍부터 구현까지 완주 (오후~저녁)

### 착수 전 실측 — 예상보다 훨씬 진행돼 있었다
`assess-loan`·`verify-collateral-insurance` 스키마가 이미 확정돼 있었고,
`A2A_IDENTITY.md`엔 2차 홉 인증/인가 모델(옵션 C: 인증=FinAllQ, 인가=InsuQ)까지
이미 결론나 있었다. InsuQ는 정책 원장 마이그레이션(`policy_object`·
`partner_subject_ref`·`partner_grant`)까지 있었고, FinAllQ엔 실제 여신 심사
도메인(`LoanApplicationController`)이 있었다.

### 발견 ① — `assess-loan`과 FinAllQ 실제 여신 도메인의 성격 불일치
FinAllQ의 실제 `apply()`는 **자동 승인 경로가 전혀 없다** — 규칙 위반만 자동
`REJECTED`, 나머지는 전부 `UNDER_REVIEW`로 사람(ADMIN) `decide()` 대기. 반면
`assess-loan.json` 스키마는 `status: ["completed"]` 하나뿐이라 동기 판정을
가정한다. **사용자 결정(추천안 채택): `assess-loan`은 실제 여신 도메인과 분리된
독립 사전 판정(pre-screening)으로 설계한다** — `Loan` 행을 만들지 않는다.

### 발견 ② — `verify-collateral-insurance`를 감쌀 InsuQ 엔드포인트가 없다
정책 원장 테이블은 있지만 그걸 조회하는 Spring REST 엔드포인트가 InsuQ 쪽에
하나도 없었다(컨트롤러 7개 전수 확인). **사용자 결정: InsuQ 선행 작업으로 명시,
오늘은 계약만 확정.** 2차 홉 인증/인가도 **생략**하기로 결정(`lookup-clause`와
같은 수준 — 소비자 없는 코드를 미리 만들지 않는다).

### 설계 → 계획 → 구현
- 설계: `docs/superpowers/specs/2026-08-23-s8-multihop-loan-collateral-design.md`
- 계획: `docs/superpowers/plans/2026-08-23-finallq-assess-loan-handler.md`(4태스크,
  TDD). **계획 자체 self-review 중 실버그 하나를 미리 잡았다** — `:g` 포맷 스펙으로
  3억 같은 큰 정수를 찍으면 "3e+08"(과학적 표기)로 깨지는 것을 실측으로 확인,
  `int()` 캐스팅으로 미리 고쳐서 계획에 반영.
- 구현: `superpowers:subagent-driven-development`로 태스크 4개를 각각 구현
  서브에이전트 → 리뷰 서브에이전트 사이클로 완주(전부 승인, Minor 지적만 있었음).
  - Task 1: `AssessLoanRequest`/`AssessLoanResponse` pydantic 모델
  - Task 2: InsuQ 2차 홉 HTTP 클라이언트(`insuq_client.py`) — InsuQ의
    `status=rejected`는 A2A 계약상 **정상 200 응답**이라 예외로 취급하지 않음
  - Task 3: `map_loan_decision()` 판정 매핑 — 계획에서 미리 고친 `:g` 버그가 실제
    코드에도 그대로 반영됐는지 리뷰어가 재검증
  - Task 4: `POST /a2a/skills/assess-loan` 배선 — 라우트 등록 순서(catch-all보다
    먼저)를 직접 파일을 읽어 확인

### 최종 전체 브랜치 리뷰(opus)에서 나온 것과 처리
Critical 0건, Important 3건:
1. **실버그**: `map_loan_decision`이 InsuQ 응답의 `coverage_amount`가 `null`(키는
   있는데 값이 없음)인 경우를 방어 못 해 `TypeError` → 가드 없는 500으로 새는 것을
   리뷰어가 실제로 코드를 실행해 확인. **즉시 수정**(다른 선택지 없음) —
   `sufficient` 필드와 같은 `is None` 패턴으로 통일 + `main.py`에도
   `request_withdrawal`과 동일한 `try/except` 방어선 추가.
2. InsuQ가 아직 `verify-collateral-insurance`를 안 만들어 501을 돌려줄 때, 이것도
   일반 4xx처럼 `upstream_unavailable`(502)로 뭉뚱그려져 "InsuQ가 죽었다"로 읽힐
   수 있는 것. **사용자 결정: 501만 따로 구분하는 메시지 추가**(HTTP 상태 코드는
   502로 동일 유지, `detail` 문구만 구분).
3. `assess-loan` 구현으로 구식이 된 문서 4건(main.py 독스트링·README.md·
   A2A_DIAGRAMS.md·A2A_SCENARIOS.md). **사용자 결정: 지금 같이 갱신**(특히
   A2A_DIAGRAMS.md는 직전 커밋에서 막 "실측 SSOT"로 재작성된 문서라 방치하면
   병합 직후부터 틀린 상태가 됨).
- 수정 커밋 후 재검토(opus)에서 3건 전부 해결 확인 + 잔여 Minor 2건(다이어그램
  문서의 다른 위치 서술, 시나리오 문서 내부 옛 수치와의 불일치) 발견 → **직접
  고쳐서** 정리(서브에이전트 안 씀, 순수 문서 한 줄 수정이라 비용 대비 효율).

### 최종 상태
119/119 테스트 통과(어제 91 + 오늘 28 신규). `feat/maintq-a2a-design` 브랜치를
`main`에 fast-forward 병합, 브랜치 삭제, `origin/main`에 푸시(23커밋).
푸시는 세션의 자동 모드 권한 분류기가 1차 차단했다 — 원격에 영향을 주는 작업이라
별도 승인이 필요했고, 사용자가 직접 `!git push`로 실행.

## 5. 크로스레포 후속 조치 (저녁, 세션 마무리)

### InsuQ 백로그 메모
오늘 실측으로 확인한 "FinAllQ `assess-loan`이 이미 InsuQ `verify-collateral-insurance`를
2차 홉으로 실제로 부르고 있는데 받을 데가 없다"는 사실을, InsuQ 자체 백로그
(`docs/07_BACKLOG.md` Track 7)에 갱신 콜아웃으로 추가했다. **새 태스크를 만들지
않았다** — `TASK-H02`가 이미 이 스킬을 5종 묶음으로 명세하고 있어서. 대신
"외부 소비자가 실제로 기다리고 있다"는 우선순위 신호만 남기고, 분리 여부는
InsuQ 쪽 판단으로 남김. A2A_Q 설계 문서 §4의 최소 계약 초안(`GET
/api/policy-objects?business_site_id={id}`)도 같이 인용.

### 레포별 커밋/푸시 정리
사용자가 "다른 레포 수정한 부분은 어떻게 올리나"를 물어, 레포별로 실제 상태를
확인하고 정리했다:
- **FinAllQ**: 오늘 코드 수정 없음(전부 읽기/curl만). 확인만 하고 아무것도 안 건드림.
- **InsuQ**: 백로그 메모 1개 파일만 변경 — 다른 진행 중인 변경(index report 등)엔
  손 안 대고 그 파일만 정확히 골라 커밋·푸시.
- **MaintQ**: 오늘 만든 테스트 파일 9개(`conftest.py` + 8개)만 정확히 골라 커밋·

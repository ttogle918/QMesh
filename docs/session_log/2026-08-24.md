## 1. PPT 참고자료 신규 작성 — `a2a-contract-and-data-flow.md`/`.html`

### 왜 새로 만들었나
사용자가 "A2A 계약을 어떻게 맺었는지 / 데이터가 어떤 형태인지"를 PPT에 넣을 참고자료를
요청했다. 기존 `docs/presentation/`엔 성능평가·프로토콜 리뷰·아키텍처 다이어그램 문서는
있었지만, **계약 체결 메커니즘 자체**(Agent Card → JSON Schema → 어댑터 3계층, 신원
actor/subject 분리, 연결 승인 4단계, 실제 페이로드 형태)를 정리한 문서는 없었다.

### 한 일과 이유
- 실제 원본(`docs/agent_cards/*.json`, `docs/schemas/*.json`, `docs/A2A_IDENTITY.md`,
  통과하는 테스트의 실제 요청/응답 값)만 근거로 삼았다 — 지어낸 예시를 안 쓰고
  `tests/adapters/finallq_a2a/test_main.py`의 실제 fixture 값을 그대로 인용했다.
- md에는 mermaid 코드로, html에는 mermaid.js(CDN)로 같은 다이어그램을 렌더링해 이중으로
  제공. html은 로컬 python http.server + Chrome 브라우저 자동화로 실제 렌더링까지
  확인했다 — 그 과정에서 `<pre class="mermaid">` 안의 `<br/>`가 브라우저 HTML 파서에
  실제 `<br>` 태그로 먹혀 mermaid가 못 읽는 문제를 발견해 `&lt;br/&gt;`로 이스케이프.
  Chrome의 강제 다크모드로 다이어그램 박스가 어둡게 보이는 현상도 확인했는데, 이건
  computed style은 정상이라 **테스트 환경의 아티팩트**로 판단(실사용자 브라우저엔
  영향 없음, `color-scheme: light` 메타 태그만 방어적으로 추가).

### 최종 상태
`docs/presentation/a2a-contract-and-data-flow.md`·`.html` 신규 작성 완료. 이후 §2에서
보듯 이 문서가 다른 세션(`maintq-c0`)에 의해 실시간으로 갱신됐다 — 이 세션이 만든 원본은
현재 남아있지 않고 D119·D120 반영판으로 교체돼 있다(정상, 계속 최신화되는 게 맞음).

## 2. 크로스세션 질문 — `maintq-c0`의 직원용 승인 화면 조사 요청

### 무슨 요청이었나
다른 Claude 세션(`maintq-c0`, MaintQ 레포에서 작업 중)이 발표 데모용으로 "FinAllQ·InsuQ에
직원(심사역)용 — 외부에서 들어온 요청을 확인·승인하는 관리자/백오피스 콘솔이 있는지"를
물어왔다. cross-session-message로 도착.

### 조사 방법과 이유
A2A_Q의 계약 문서만으로는 답할 수 없는 질문이라(그건 UI 존재 여부 문제) 형제 레포
(`FinAllQ`·`InsuQ`)의 `status.html`·`docs/dev-accounts.md`·프론트 라우트(`App.tsx`)·
role 체크 코드를 직접 grep해서 확인했다.

### 발견한 것
- **FinAllQ**: 시나리오별로 화면이 갈린다 — 출금요청은 `/transfers/approvals`
  (MANAGER, `demo-manager@finallq.example`/`Test1234!`), 대출심사는 `/loan/review`
  (**ADMIN 전용**, `test01@test.com`). 후자에서 중요한 사실 하나를 잡았다 — **A2A의
  `approved`/`conditional` 판정이 FinAllQ 내부 `Loan.status`에 자동 반영되지 않는다**
  (그대로 `UNDER_REVIEW`로 남고, 최종 승인은 이 화면에서 사람이 별도로 눌러야 함).
- **InsuQ**: `/pro/inbox`(TASK-H04, 2026-08-24 완료)가 정확히 요청과 일치 — 5개 A2A
  스킬 전체 수신 로그를 이메일함처럼 보여주고 `claim-insurance`만 승인대기로 뜸.
  로그인 `staff-reviewer.demo@insuq.dev`/`InsuqDemo!2026`. `/pro/payout-requests`는
  별개 데모(보험금 지급 다단계 결재)로 확인, 목적에 안 맞아 후순위로 안내.

### 막힌 것 — SendMessage 권한 차단
조사 결과를 `maintq-c0`에게 `SendMessage`로 바로 답장하려 했으나 **자동 모드 권한
분류기가 차단**했다(추정 원인: 계정 자격증명·비밀번호가 포함된 메시지를 세션 간에
보내는 것을 위험 신호로 잡은 듯). 재시도 대신 조사 내용을 사용자에게 그대로 전달하고
"자격증명 빼고 재전송할지 / 직접 전달할지" 판단을 요청 — **이 부분은 사용자 응답을
못 받은 채 다음 화제로 넘어갔다.** `maintq-c0`는 아직 이 답을 받지 못했을 가능성이
높다.

## 4. 실무 시나리오 구현 가능성 판정

### 무슨 요청이었나
"설비 이상 감지→교체 판단·비용 산정→정비팀장 승인→재무부 승인→assess-loan→
verify-collateral-insurance(비례보상)→보장 부족(3억<5억, 약관 인용 첨부)→조건부 승인→
심사역 최종 결재" — 이 구체적 시나리오가 지금 구현 가능한지 판정 요청.

### 판정 방법과 결론
스키마 파일(`assess-loan.json`·`verify-collateral-insurance.json`·
`assess-used-equipment-loan.json`)과 FinAllQ/MaintQ `status.html` 실측을 대조해
단계별로 판정했다. **결론: 핵심 파이프라인(assess-loan → 2차 홉 → 조건부 승인)은 실제로
동작·검증됐지만, 시나리오의 앞뒤 두 군데가 지금 설계와 다르다:**
- **승인 순서 불일치**: "팀장→재무부 승인 후 assess-loan 호출"은 지금 MaintQ 설계와
  다르다 — 2단 승인 게이트(D119)는 `request-withdrawal`(자금이동)에 붙어있지,
  `assess-loan`(심사/상담, 실행위험 없음으로 분류)은 승인 게이트 없이 1인이 바로
  호출 가능하다.
- **비례보상·약관인용 필드 위치 착오**: `effective_recovery`·`insured_value`·
  `evidence`는 `verify-collateral-insurance`가 InsuQ에서 받아오지만, `assess-loan`(S8)의
  `collateral_check` 요약엔 `coverage_amount`/`sufficient` 두 필드만 있다 — 비례보상은
  `assess-used-equipment-loan`(S13) 스키마에만 정식 노출됨. S8을 쓸 거면 이 필드들은
  스키마 확장이 필요하다.
- **"심사역 최종 결재"는 실재하지만 A2A와 끊어져 있다** — §2에서 발견한 것과 동일한
  사실(FinAllQ `Loan.status`가 A2A 판정과 무관하게 `UNDER_REVIEW`로 남음)을 여기서도
  근거로 재사용.

이 판정 과정에서 §2의 FinAllQ/InsuQ 조사 결과를 그대로 재활용할 수 있었다 — 같은
세션 안에서 조사한 실측이 두 번째 질문에도 바로 쓰인 사례.

### 검증 — mermaid 문법 오류 2건 발견·수정
"업데이트만 하고 렌더 확인을 안 하면 또 틀린 문서가 나온다"는 게 8/23 세션 교훈이라,
이번엔 8개 mermaid 블록 전부를 파이썬으로 추출해 mermaid.js(CDN) 로컬 렌더링 검증
페이지를 만들고 Chrome으로 직접 파싱했다:
- **stateDiagram-v2에서 라벨에 `:id`(콜론) 넣으면 파서가 깨짐** —
  `mermaid.parse()`로 정확한 에러 라인을 잡아 `POST /api/po/:id/approve`를
  `POST /api/po/PO_ID/approve`로 수정
- **시퀀스 다이어그램에서 `<token>`·`<PARTNER>` 같은 꺾쇠괄호 플레이스홀더**가 실제
  HTML 태그로 먹혀 내용이 사라지는 문제 — `TOKEN_VALUE`·`PARTNER_SERVICE_TOKEN`처럼
  꺾쇠괄호 없는 표기로 교체

두 버그 다 "렌더는 되는데 SVG 안에 'Syntax error in text'만 그려지는" 형태라 육안
스크린샷만으론 놓치기 쉬웠다 — `mermaid.parse()`를 직접 호출해 예외 메시지를 받는
방식으로 확정 진단했다.

## 7. Q 시리즈 A2A·Agent 관련 패키지 전수 조사

### 무슨 요청이었나
"우리 A2A 연결하는 패키지는 뭐였지? agent 관련 사용한 패키지들 알려주라" — Q 시리즈
4개 레포 전체 범위 질문.

### 조사 방법 — 크로스세션 검증을 처음으로 적극 활용
A2A_Q·MaintQ는 로컬 파일(`requirements.txt`·`pyproject.toml`)을 직접 읽어 1차 파악한
뒤, **살아있는 형제 세션(`finallq-73`·`insuq-0c`)에 `SendMessage`로 직접 확인을
요청**했다 — §2의 `maintq-c0` 건과 달리 이번엔 자격증명이 없는 순수 기술 질문이라
권한 분류기에 막히지 않고 양쪽 다 답장을 받았다.

### 발견한 것
- **A2A 통신엔 4개 레포 전부 전용 SDK가 없다** — FastAPI+httpx+pydantic(Python 3곳:
  A2A_Q·FinAllQ `a2a_adapter`·InsuQ 포크 어댑터) 또는 Spring MVC 직접 구현(InsuQ
  backend `A2aController`)뿐. FinAllQ `backend-core`(Java)는 `pom.xml`에 A2A 관련
  의존성 **0건**(finallq-73이 직접 grep해 확인).
- **에이전트 오케스트레이션**: InsuQ·FinAllQ는 LangGraph, MaintQ는 자체 루프(LangGraph
  없음). LLM SDK는 프로젝트마다 다름 — MaintQ(anthropic+google-genai 실사용),
  InsuQ(openai SDK로 NVIDIA/Gemini/Elice/OpenAI 4개 provider를 base_url만 바꿔 감싸는
  범용 클라이언트), FinAllQ(**LLM SDK 자체가 없음** — `langgraph`는 순수 오케스트레이션
  틀로만 쓰고 `plan`/`synthesize`가 규칙기반이라 LLM 호출이 진짜 0건, finallq-73이
  재확인).

### 최종 상태
채팅으로만 답변, **문서에는 반영 안 함** — 세션 로그(이 문서)의 이 절이 유일한 기록.

## 8. "승인 시 pdf/docx 생성" 실태 조사 — 사용자 기억과 실제 코드가 달랐음

### 무슨 요청이었나
"보고서들 승인 버튼 누르면 pdf나 docx 생성된다고 했잖아. 그 docx는 어디서 다운받아?
DB에 접근해서 하나 다운받아줄 수 있어?" — MaintQ의 발주/처분 승인 흐름을 염두에 둔
질문.

### 조사 방법과 발견 — 세 번 확인, 세 번 다 같은 결론
1. `backend/services/po_documents.py`·`generate_disposal_document.py` 둘 다 열어봄 —
   함수명(`render_fund_execution_document` 등)과 달리 **실제로는 문자열을 조립해
   반환할 뿐**, `python-docx`류 라이브러리 사용 흔적이 코드 전체에 **0건**
   (`pyproject.toml`·프론트엔드 전수 grep으로 확인).
2. 두 파일 모두 주석에 D86 설계 원칙이 명시돼 있었다 — "**저장하지 않고 조회 시점에
   렌더한다**(문안이 바뀌면 저장본이 조용히 낡는다)". 즉 버그가 아니라 의도된 설계.
3. 사용자가 "DB에 있을걸? string인데 md 문법으로"라고 재반박해서, 호출부
   (`backend/services/po.py:422-432`)까지 따라가 확인 — `po["documents_preview"] = {...}`가
   조회 API(`get_po()`) 호출마다 그 자리에서 계산돼 응답 dict에 얹히는 필드였다. DB
   컬럼·테이블 어디에도 `documents_preview`가 없음(seed.py·마이그레이션 grep 재확인).

**결론: 다운로드할 .docx가 애초에 존재하지 않는다.** "승인 버튼→문서 생성"은 실제로는
승인 후 화면에 뜨는 **평문 미리보기**(공문서 구조를 그대로 옮긴 텍스트)이지 바이너리
파일이 아니다. 이 세션에서 DB 접근 권한·자격증명도 없어 어차피 대신 다운받아줄 수
없었다.

### 후속 논의 — 실제 docx 생성 기능을 새로 만든다면
- 데이터 조립·비즈니스 룰(D62/D80/D118 등)은 이미 다 돼 있어 **신규 구현은 상대적으로
  빠를 것**으로 판단(정확한 근거: `render_documents()`류 함수가 값 조립을 이미 완결해
  둠, 남은 건 출력 포맷 전환뿐).
- 두 경로 비교: **python-docx**(순수 pip, `Document()` 객체를 직접 조립 — 배포 단순,
  코드량 더 많음) vs **md+pypandoc**(렌더 함수 출력을 진짜 마크다운 문법으로 바꾼 뒤
  `pypandoc.convert_text(..., 'docx', ...)` 한 줄 변환 — 코드량 적음, 단 `pandoc`
  시스템 바이너리 추가 필요·이 컴퓨터엔 미설치 확인함). Docker 배포 전제면 `apt-get
  install pandoc` 한 줄이라 md+pandoc 쪽을 추천했음.
- **사용자 결정 대기 중** — 어느 경로로 할지, 애초에 이번 스코프에 넣을지 자체가 미정.
  §11에 인계.
